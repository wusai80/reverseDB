## 1. 要保留的能力与删除单位

保留入口是应用适配器 `TpccApp.reference` 的 OrderStatus 分支。保留完整订单头、按行号排序的全部订单明细、客户/订单缺失错误及数据库状态。客户与订单数据是参数，未被样本使用的数据不据此排除。

删除单位是 `OrderStatus.getOrderLines` 及专属 `ordStatGetOrderLinesSQL` 定义，并移除适配器对应调用。这个方法原来每次都执行，但返回的展示字符串列表在该入口被丢弃。生成完整 JSON 的两条查询继续执行。

原 BenchBase 终端入口、任意外部反射入口及诊断/查询观察不属于此次保留能力。特化版将终端 run 替换为明确拒绝的桩，不能拿它替换完整 BenchBase。没有声明五类事务及全部外部入口均在本轮得到验证。

环境条件沿用此前明确声明：串行固定快照，被删区域正常完成，无保留观察所需的查询外部副作用。这些是条件，不是测试证明的事实。客户不存在、无订单等业务错误仍需保留，不能混入“正常执行”而排除。

## 3. 本轮补上的源码论证：分支与接收对象

冻结适配器中有如下结构：

```java
String type = cmd.getString("type");
// NewOrder 的单独分支正常执行后直接返回。
TPCCProcedure p = switch (type) {
    case "Payment" -> new Payment();
    case "OrderStatus" -> new OrderStatus();
    case "Delivery" -> new Delivery();
    case "StockLevel" -> new StockLevel();
    default -> throw new IllegalArgumentException(type);
};
p.initialize(DatabaseType.POSTGRES);
switch (type) {
    case "OrderStatus" -> {
        // 客户和订单读取
        invoke(p, "getOrderLines", c, 1, d, order.o_id, cust);
        // 完整 JSON 生成
    }
    // 其他分支
}
```

以上是说明结构的摘录，完整源文件位置列于证据索引。手工推理如下：

1. 到达该调用点，意味着进入后一个 switch 的 OrderStatus 分支，因此局部 `type` 为该字符串。
2. 两个 switch 使用同一个局部 `type`，其间没有重新赋值。String 值不会因为后续命令对象变化而改变。
3. `p` 的赋值先于该调用；在相同 type 下选择 `new OrderStatus()`。该局部 p 没有后续重新赋值。前面 NewOrder 块中的同名 p 属于另一个作用域。
4. 因而凡到达此调用点的执行，p 都是这一 OrderStatus 实例；无需限定具体客户、订单或测试数据。
5. 固定版本的反射桥按声明方法名和参数数量匹配，提取结果在 OrderStatus 中发现一个相符方法。由此可以排除“这里 p 实际是其他三种事务对象，所以找不到该方法”这一个疑问。

形式上，本例支持条件断言：

```text
到达指定调用点 ∧ 使用已绑定源码/制品
    ⇒ type = "OrderStatus" ∧ runtimeClass(p) = OrderStatus
```

这只是来源绑定下的手工源码推理，不是自动路径证明。它也不推出调用不会失败：反射访问、参数、被调用方法、JDBC 和资源等仍有各自条件。自动提取器仍记录四种接收者的保守集合；旧提取证据与 unknown 结果均不修改。

软件工程分析在此补足了实例测试无法覆盖的参数化关系；实例中的正常执行只提供相符证据，不承担这条断言的证明。

| 专属/共享资源 | 专属 SQL 字段与方法一并删除；共享工厂保留 | AST 显示多个共享消费者，模型拒绝连同共享部分删除 |
| 调用与构建 | 删除选定调用、阻断排除的入口、处理字段注册与反射 | 此前特化源码差异、编译及实际类加载支持；不推广到其他变换 |

| 对删除理由的挑战 | 已有证据 | 判定变化 |

反证必须对应某一项删除理由，而非随意增加测试事务。新增消费者、未知入口或副作用不是“测试噪声”，会改变需求或契约。
