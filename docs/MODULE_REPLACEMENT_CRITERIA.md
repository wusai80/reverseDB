# 模块删除与融合替代：判据及三个小案例

2026-11-06。本轮只建立判据、给出条件化论证并检查小模型。没有扩建分析器、增加数据库实验或优化实际应用。

核心结论：**必须保留的是能力所需的作用，不必是实现该作用的原模块。** 依赖图帮助找出待履行的义务；删除和融合必须分别判断。此前需求闭包的工作已经讨论过条件化删除，本轮新增的是统一的替代关系及边界粒度分析。

## 1. 研究问题与定义

固定能力契约 `C=(I,A,O)`：I 是允许的输入，A 是环境和状态约束，O 是必须保留的观察。其范围由能力要求确定，不由测试覆盖决定。

对一个拟替换区域 M，在入口与出口选择边界 K。K 包括：

- 后续计算真正使用的值，以及需要保留的对象身份／别名关系；
- 完整业务状态及相关事务工作区，未被本次请求访问的数据也保留；
- 正常退出、业务中止、允许范围内的错误和终止性；
- 若契约要求观察，则还包括外部事件及其中必要的顺序。

只有后续不再使用、也没有可观察作用的临时表示才能不进入 K。例如，合并区域内部的暂存数组可以改变表示；业务表中未访问的行不能据此排除。

定义 `M ≃(C,K) N`：对 C 允许的**所有**边界输入与状态，M 与 N 的执行在 K 上给出相同观察。若内部表示不同，需给出入口／出口状态的对应关系；不能默认 Java 对象、SQL 数值和文本具有相同语义。本轮具体小模型都是确定性、有限完成的串行执行，比较完整模型状态，不涉及并发调度。

### 条件化替换规则

如果同时满足：

1. 到达区域入口时 C 确实成立；
2. K 覆盖区域对保留上下文的全部影响，外部不能观察到被省略的内部步骤；
3. 有证据建立 `M ≃(C,K) N`，包含退出状态、业务效果及契约要求的异常／顺序；

那么在这个上下文中可以用 N 替换 M。

论证思路：前缀将两个程序带到对应入口状态；第3项使出口在 K 上对应；第2项保证后续程序只能使用这些已保留的信息，因此产生相同的必需观察。若区域可能不终止，还须匹配不终止行为，不能只比较成功出口。并发环境若能观察区域内部步骤，第2项不能直接成立。

这是一条充分条件，不是任意程序的可判定完整判据。局部同类型、同写入列或一次最终状态相同，均不足以建立这三个条件。

## 2. 删除与替代的区别

删除是替代关系的特殊情况：候选 N 为不产生作用的 skip。它要求原区域对 K 没有需要保留的作用。

| 结果 | 所需依据 | 含义 |
| --- | --- | --- |
| 条件化可删 | `M ≃(C,K) skip` | 在给定能力与边界下，可以省去该区域 |
| 不可直接删 | 有合法反例使 M 与 skip 的观察不同 | 该作用必须由某个实现承担 |
| 条件化可替代 | 给定具体 N，建立 `M ≃(C,K) N` | 原实现可被 N 替换，包括跨层融合 |
| 未知 | 无反例，但关键义务未闭合 | 保留原路径，不能把少量测试通过当作删除许可 |

“不可直接删”与“可替代”可以同时成立。这是本轮对先前 keep/delete 讨论的关键补充：数据和效果依赖存在时，应保留义务，而不是永久冻结原布局。反过来，也不能把潜在替代方案的存在当成已经找到安全实现。

判据是上下文相关的。同一方法在展示入口可能必要，在不需要展示的入口可能可删；要物理删除共享代码，还必须核查所有保留调用者。这一点不由单个调用点的替换论证自动推出。

## 3. 三类区分性案例

### A. 被调用但可删：未消费的展示结果

模型先读取并格式化完整记录用于展示，随后另行返回完整业务记录。若契约不观察展示、格式化区域正常完成且没有可观察副作用，删除展示区域不改变 K。其存在于调用图中，不足以证明它必要。

两个最小契约变化立即推翻删除：

- 若展示查询可以失败并阻止后续返回，原版可能失败而删减版成功。
- 若重新要求展示输出，删减版缺少该观察。

这与既有 OrderStatus 案例一致：只是在指定入口和环境条件下省去展示工作，不删除 order_line 数据，也不授权删除其他入口需要的功能。

### B. 返回值未使用但不可删：记账写入

模型包含两个账户的完整余额，模块给第一个账户增加正金额，返回值被丢弃，最终响应固定为 ok。删除模块仍返回 ok，却改变完整余额状态。第二个账户保持原样，也仍参与状态比较。

因此“返回值无人消费”只能排除一种数据依赖，不能排除写入效果。判据必须包含状态，不能仅检查应用返回结果。

### C. 作用不可删但实现可替代：库存阶段融合

模型抽取 NewOrder 的库存顺序语义。原版先读取每一行并暂存计算值，再按输入顺序写库存；同一商品可重复出现。库存记录含 quantity、ytd、count，全部记录和完整有序订单行都属于观察。

令初始库存数量为 Q(i)，输入行 k 的商品为 i(k)、数量为 q(k)，库存变化函数为 f。对商品 i，令 L(i) 为它最后出现的位置。原版执行后的结果是：

```text
quantity'(i) = f(Q(i), q(L(i)))
ytd'(i)      = ytd(i) + Σ q(k)，求和范围为 i(k)=i
count'(i)    = count(i) + 出现次数(i)
```

没有出现的商品，其完整记录保持不变。

另一种实现可以按商品汇集输入行，使用最后一行计算最终 quantity，累计数量和次数，并保留原有订单行顺序。它在这个无中间观察、无触发器、串行纯状态模型下产生同样结果。上述等式对任意有限合法行序列成立：所有 quantity 暂存值都来自同一初始 Q；顺序绝对赋值最终保留最后一个值；两个增量字段分别按原次数累加。

这给出了模型内的参数化论证，有限枚举只用于检查实现和反例。它不是对真实 Java/SQL 的自动证明：模型没有覆盖 Java 溢出、浮点金额、锁、约束、触发器或完整订单表写入，也没有生成或批准一个新的数据库聚合后端。

错误候选把读取和写入改成逐行交错。若初始 quantity=10，同一商品连续两行各取1：原版两次均读取10，最终 quantity=100；错误候选第二次读取已变为100的库存，最终为99。两者返回的订单行完全相同。

这不是数据裁剪问题，而是读写依赖与执行阶段改变。已有真实五行 NewOrder 反例也出现原版76、错误版75，本轮只核验其归档，不重新运行数据库。

## 4. 粒度为什么会影响判据

若只考虑读取阶段，其暂存结果会被后续写入消费，必须纳入出口 K，不能直接删除。若把读取和对应写入一起纳入候选区域，暂存结构可能成为内部表示；只要完整效果和出口值保留，就允许不同内部实现。

所以粒度应随可闭合的依赖边界确定，而不机械地固定为类或函数。真实 NewOrder 中间还包括 order_line 写入，不能用这个只含库存的子模型忽略它：实际替换区域必须覆盖或正确保留这些额外作用。区域越大，需要承担的证明义务也越多，并非越大越好。

## 5. 固定小模型结果

模型只用一个独立 Python 文件，标准库即可运行，不接入现有优化器。具体范围预先固定：展示列表长0～3、元素0～2；记账两个余额0～2、金额1或2；库存两种被访问商品、三种行数量、行长1～3，外加一条从不访问但必须完整保留的记录。

| 对照 | 固定比较数 | 结果 |
| --- | ---: | --- |
| 正常、展示不必需时删除展示 | 40 | 完整模型状态与响应相同 |
| 展示查询故障／展示重新成为必需 | 各40 | 均能推翻原删除条件 |
| 删除返回值被丢弃的记账写入 | 18 | 响应相同，完整状态不同 |
| 原库存阶段与替代实现 | 2,064 | 完整状态和有序结果相同 |
| 同一库存输入上的提前写错误候选 | 同上 | 1,872 个状态差异，全部被只看响应的方法漏掉 |
| 缺失商品中止 | 24 | 三个模型实现的状态均完整回滚 |

库存模型8个初始状态×258个行序列；计数是有限模型比较，不是2,064类真实 TPC-C 能力或业务执行。短行序列用于研究依赖机制，不修改真实应用5～15行的入口条件。中止比较匹配状态与结果，不要求任意故障时刻相同。

## 6. 本轮得到与未得到的结论

已得到：一组能区分“调用但可删”“返回无用但不可删”“作用必要但可替代”的判据和反例，以及库存子模型的参数化论证。相对单纯可达性，它能许可无观察贡献的执行区域删除；相对返回值使用判断，它能拒绝有必要效果的删除；相对永久保留原实现，它允许跨层融合。

尚未得到：从反编译结果自动恢复完整 C/K，以及自动证明真实候选满足替代关系。观察等价、效果摘要和依赖分析本身都是基础方法；本项目可能形成的研究贡献在于如何从应用—数据库交互恢复足够的边界义务，并用它们支持跨模块重组，不能仅以这个小模型宣称新算法。

下一步值得讨论的是：选定一个真实融合区域，哪些边界义务已由源码和端到端证据支持，哪一项仍阻止判定。先找到决定性缺口，再考虑补方法。本轮不新增规则库、静态分析平台或性能实验。
