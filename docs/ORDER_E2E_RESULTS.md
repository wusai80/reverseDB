# 顺序关系候选的同协议端到端验证

2026-11-06。四个版本各执行70条固定请求，共280条，完成真实提交／回滚及完整九表比较。**正常融合和独立结果查询换序均与原版一致；提前写库存产生可持久化的状态差异。** 这为前三个真实候选提供了同一验证口径的结果标签，本轮没有拟合概率或测量性能。

## 固定对照

复用已有五组70请求协议，包括五种事务、重复商品、普通／极大合法时钟、业务中止和输入拒绝。顺序、输入、四个串行终端连接、完整初始数据及场景夹具均保持一致；每个场景、每个版本独立恢复数据库。

原版经过 `TpccApp.main` 原入口。三个候选共用修复后的Java时间绑定与同一Payment融合，只替换数据库内NewOrder函数体。为保持追踪器接受的精确JDBC签名，候选分别在隔离数据库中安装为同一个 `neworder_full` 名称；每次从 `pg_proc.prosrc` 取回实际安装函数体并逐字节核验，避免名字相同却测错版本。类加载、JDBC次数和commit／rollback事件均有核对。

测试保留UTC、SERIALIZABLE、fsync、同步提交与完整WAL。基础库共599,051行；warehouse、district、customer、item、stock、oorder、new_order、order_line、history九表均比较完整行数与全字段、全行哈希，保留重复行数量。最终状态由应用退出后的独立psql连接获取，不只比较被访问的行。

正常融合与换序候选的完整响应、逐请求观察、初末九表状态全部一致。所有版本五项业务一致性约束均通过，说明这些约束及成功率都不足以检测该类错误。原版四组旧场景还与此前归档逐项一致。极大时钟在四版均提交1条infinity订单和2条infinity付款历史。

## 反例及不能省去的状态观察

提前写入在baseline、transaction_edges、delivery_edges三组未产生本次可观察差异；在holdout和time_boundaries两组出现差异。

- holdout中的 `new-05`：原版库存数量76，提前写入为75。
- time_boundaries中的两条重复商品订单提交后，库存状态不同，并延续到后续请求的状态观察。
- `edge-new-abort` 的跨版本状态也不同，但各自中止请求的before／after观察一致。差异来自此前已提交的错误库存，不是本次回滚失败。20次业务中止的已记录before／after观察均一致；这不等于逐请求扫描了全部九表。

完整响应包括业务 `result` 与 `state`。剔除state字段后，四版所有响应字段仍相同；订单返回结果、成功率或SQL执行成功本身都会漏掉这个错误。完整响应差异位于state，应用退出后的完整stock表哈希进一步确认了真实持久化差异。
