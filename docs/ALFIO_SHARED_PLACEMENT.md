### 实际测试到的边界

运行官方JAR中的原`reserveTickets`辅助方法和原`reserveTicketsForCategory`方法，使用原NPJT、原自定义参数转换器／列映射器和真实PostgreSQL。完整恢复既有63表夹具，保持20张票、默认READ COMMITTED及应用角色／RLS上下文；事务由本地测试调用者显式管理。

成功的外层路径在最后一次类别读取及映射完成后，由观测代理抛出专用测试终止信号，阻止进入后续初始化／写入。原数量检查失败和原数据库缺失行异常不经该终止信号替换。这是**真实原代码的局部边界测试，不是完整Spring代理、HTTP或事务生命周期的端到端等价测试**。

外层方法在目标片段之前还有`fixToken`的一次类别读取；日志完整记录这次读取。因此成功外层日志有4次repository调用，其中目标片段是后面的3次，不能把它们误计成4→1候选。

### 九场景结果

| 场景 | 观察结果 |
|---|---|
| bounded类别 | 原分支按ID返回完整列表`[1,2,3]` |
| unbounded类别 | 原分支选择未分配类别的票，返回`[1,2,3]`；修改回滚 |
| 等待队列状态 | 原RELEASED／PRE_RESERVED过滤返回`[1,2]`；修改回滚 |
| 竞争连接锁住1、2 | 原SKIP LOCKED返回`[3,4,5]`；另一个连接NOWAIT锁3失败`55P03`，锁6成功；调用者回滚后锁3成功 |
| 竞争锁导致数量不足 | 实际外层抛原`NotEnoughTicketsException`，仅得到票20，未执行最后类别重读；票20仍锁定直到调用者回滚 |
| 静态完整类别对照 | 两次类别模型完整相同，成功达到重读后的终止点 |
| READ COMMITTED并发修改 | 初读价格1000、bounded=true；选票及数量检查之后提交修改，重读为价格2000、bounded=false；完整模型不同 |
| REPEATABLE READ对照 | 同样的并发提交下两次都看到原值；仅是机制对照，不授权改应用隔离级别 |
| 并发停用类别 | 初读成功，选票之后类别变为NOT_ACTIVE，原重读抛`EmptyResultDataAccessException`；复用早先对象会丢失这个异常 |

并发顺序由“进入最终类别查询前同步执行另一连接的UPDATE并提交”明确控制；锁验证使用实际独立连接和NOWAIT，不靠猜测睡眠时长。测试没有给被测应用增加数据库能力，也没有实现优化候选。

## 最新：账单／审计片段的效果契约（2026-11-06）

对上一轮发现的2调用片段进一步核实了原参数、Java数值计算、异常前缀及事务归属。该区域现在明确为4阶段：**原账单参数准备 → 原UPDATE返回 → 原Java审计参数及Date构造 → 原审计INSERT**。作为原父级片段的重叠细化加入第9个语义作用域；父子不得累计为额外调用。

决定性边界是位于两条SQL之间的`new java.util.Date()`。冻结Manager字节码的UPDATE调用在指令146、Date构造在160、审计调用在163；JDK17的无参Date构造器调用`System.currentTimeMillis()`。此区间无控制跳转／方法内异常处理，UPDATE异常会在原Date构造前传播。取时必须保持在原UPDATE成功返回之后、审计执行之前。此义务之前已有文字声明，本轮将其拆成独立、显式host保留节点，并给父级`audit_creation`同步加上保留约束。

### 参数与副作用保持

- 账单保留全部10个绑定参数，包括原VAT状态、原Java `int`计算、`Math.abs`、货币及原null／false参数。`Integer.MIN_VALUE`的abs行为与整数溢出不改成SQL数学整数语义，也不靠限制数据域避开。
- 审计保留全部8个叶子参数、原reservationId引用、Java Date对象与毫秒值；原默认方法补入的`modifications=null`不变。参数对应关系是核对冻结源码后给出的摘要，不声称自动恢复任意Java栈／别名。
- UPDATE和INSERT的`int`结果后均有POP；原代码不检查是否更新一行。因此不能新增“影响0行就跳过审计”的逻辑，不能把返回值未使用等同于SQL无效果。
- 原Java参数求值失败先于UPDATE；UPDATE失败不执行后续取时和审计；审计失败继续交由原事务所有者处理。保留类级Spring事务、连接／权限上下文；没有增加提交、回滚或保存点。

### 同一选择器的结果与边界

真实契约交给第一项目原DP，调用数仍为2、数据库区域0。另作明确标记的合成对照：仅为隔离取时约束，给两条语句假设可用数据库能力、完整编码及选择器支持的占位SQL，原Java取时节点继续保留。选择器仍无法跨越该节点，也不会选择无调用收益的单条迁移。这个对照没有准入alf.io后端，也没有替换真实SQL。

因此在当前契约及单次数据库调用模型下，**停止推进此处UPDATE＋审计的2→1融合**。不提前读取时间、不换成数据库时间，也不引入服务器回调Java等新执行协议。此结论限于该片段，不表示全系统没有优化机会。

补充确定性的效果模型反例：若原UPDATE执行期间主机时间从100变为200，原顺序审计时间为200，提前取时为100。它是源码顺序对应的模型反例，**不是新执行的Java／数据库测试**。固定所有时钟读数的回放可能掩盖这种差异，不能单独证明移动取时的合法性。

[alfio_placement_contracts.py](../scripts/alfio_placement_contracts.py)只建立输入事实与契约，不包含区域选择算法。它使用锁定的字节码事实、原样反编译源码和已有契约证据，将原方法分为三个完整阶段：

1. Java参会人选择、姓名／元数据／VAT校验和全部参数物化。
2. 原JDBC批次执行。
3. Java计数求和、整数收窄及返回。

值依赖连接完整参数序列和完整计数数组，控制依赖保留“全部参数构造完成后才写入”。粒度是人工源码摘要，与第一项目的前端信任边界一致，尚非任意Java语义的自动恢复。

零JDBC的参数构造阶段被限定到原 `initTicketsForReservation` 普通分支的内存参会人供应函数，绑定对应调用点与lambda字节码。**任意 `IntFunction` 可能自行访问数据库，不能无条件记为零成本。** 未知供应函数输入被拒绝；自定义模型子类、集合回调或序列化器不属于该摘要的已知域。

非空批次成本为一次execute，空批次为零；证据同时来自原方法的一处批次调用和已有实际JDBC轨迹。1／2／3张票的观测规模没有变成合法输入上限。原模型只接受非负仿射成本，因此空／非空分支分别提供契约，没有偷偷把指示函数或新成本算法加入选择器。

未接入的上层预订、附加字段、价格、账单、审计、扩展路径列入覆盖缺口，没有把未知调用成本补成零后假装优化整个事务。

## 实际拒绝与成本诊断分开记录

原SQL注解完整保留，包括命名参数、`'PENDING'`、`::jsonb`、`::VAT_STATUS`。第一项目的受限SQL语法不能识别这条原语句，因此产生 `unknown_sql_effect`。既有实验函数仍是局部验证产物，存在底层批次异常诊断差异，没有升级为通用信任声明，因此同时产生 `unverified_lowering`。

这些是本轮**实际**选择器的准入结果。空输入还受到原有 `may_add_call_at_legal_minimum` 保护，避免把零调用变成一次调用。

另作条件化成本计算，不绕过准入、不生成代码：

- 非空分支：原路径目标 `(1,0,0)`；假设单个批次区域以后合法，目标为 `(1,1,1)`，仍输在“少移动单元”的平局项。
- 空分支：原路径 `(0,0,0)`；假设增加数据库调用为 `(1,1,1)`，会增加执行次数。

因此可以说“即使当前小候选以后合法，它也没有原目标中的调用收益”，但不能把这个条件化结论说成已经证明整个alf.io没有可融合区域。
