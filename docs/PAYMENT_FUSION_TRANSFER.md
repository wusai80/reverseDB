通用 SQL 效果提取、读写依赖和区域划分规则可以直接用于 Payment，无需修改上一轮算法。不过，当前整段 Payment 融合被拒绝：其 Java 浮点计算、可变 Customer 对象、信用分支和字符串处理尚无合格的后端语义规则。没有为了得到整段区域而把这些对象伪装成 JSON 或放宽 unknown。

## 为什么选择 Payment

Payment 同时包含多表写入、读回对象及数据驱动的条件更新，可以检验规则能否从 NewOrder 的固定阶段迁移到另一种结构。其单表 SQL 已在现有语法范围内，便于分离“SQL 效果能够识别”与“业务计算能够迁移”这两件事。

StockLevel 的关联聚合、Delivery 的排序限行、删除和聚合会首先遇到 SQL 语法支持缺口；本轮不同时扩大解析器。只深入一个事务，不继续扩大候选清单。

## 实际复用与新摘要

[迁移实现](../scripts/payment_fusion_transfer.py)使用现有带类型的 Java 提取器重新分析冻结的 Payment 源码及适配器，恢复九处反射辅助调用的唯一目标、实参对应、源位置和 JDBC 绑定。十项类内 SQL 定义均被原 SQL 效果提取器识别；应用实际使用九项，加最终客户投影共有十个静态 SQL 位置。这里按条件分支并集计数，不是一次事务执行十条 SQL。

姓名查询仍保留在类的 SQL 清单中，当前应用按客户编号访问，因此它不进入本次入口路径。没有删除这个方法、SQL 定义或任何客户数据。

能够直接复用的部分包括：

- warehouse 和 district 的先写后读依赖。
- customer 的先读后写依赖，以及更新后读取返回值的依赖。
- 多表写入的顺序、外层事务边界、未知效果与未知表示的屏障处理。

新加入的是源码绑定的 Payment 阶段摘要。金额、Customer/Warehouse/District 对象、原地字段修改及字符串规则均标记为未完成的后端义务。类型标记只是摘要中的需求描述，不代表已有转换实现。

提取器能够定位 `cust.c_credit.equals("BC")` 的 true/false 分支，但不能证明整个对象字段条件的运行语义。三个条件调用——`getCData`、`updateBalanceCData`、`updateBalance`——因此作为一个保守的分支单元保留。该单元的 SQL 效果取并集，不能把两条互斥更新直线串接执行。

最终图有 12 个节点、78 条带理由的依赖边。只有最终客户结果投影成为一个单节点结构候选；它不是有运行收益的融合实现，也没有生成独立执行版本。整段 Payment 准入明确拒绝。

## 实际代码探针发现的语义义务

[Java 探针](../prototype/module_pruning/PaymentSemanticsProbe.java)加载并核对原适配器和反编译重编译 JAR 的类来源，调用实际 `TpccApp.reference`，进而执行实际 Payment 方法。输入均通过原 AppRuntime 验证。JDBC 边界替身提供确定的字段值并记录参数与调用，不实现 PostgreSQL、事务、约束或驱动编码。

测试数据是显式边界夹具；没有证明这些状态能由既有固定事务序列生成，也不以它们限定合法数据范围。五个例子分别检查普通／较大余额、金额文本、客户数据长度和仓库名称长度。

### 1. 十进制 SQL 不能直接代替 Java 浮点链

实际适配器先将输入 BigDecimal 转为 float；Customer 的余额及累计支付字段也是 float。更新计算完成后再通过 `setDouble` 传给数据库。仓库和地区的金额绑定则经过 `BigDecimal.valueOf(paymentAmount)`，不是直接使用原输入 BigDecimal。这些是不同消费者上的转换链。

| 初始余额 | 支付输入 | 实际客户更新绑定的 double | 对绑定值按分舍入的诊断计算 | 直接十进制相减 |
| --- | --- | --- | --- | --- |
| 10.00 | 0.01 | 9.989999771118164 | 9.99 | 9.99 |
| 262144.00 | 0.01 | 262143.984375 | 262143.98 | 262143.99 |

小余额例子说明浮点误差不一定改变分位结果；较大余额例子则构成直接改用十进制减法的具体差异见证。表中的分位值用 Java BigDecimal 明确计算，本轮没有实测 PostgreSQL 存储转换，不能据此声称完成数据库差分。

交互进度中曾将第二例误报为 262144.00，读取完整探针输出后已即时更正；归档与本表均使用实际绑定的 262143.984375。

### 2. 付款金额的文本表示也是数据效果

输入 `0.10` 时，原坏信用路径把 float 拼进 C_DATA，得到：

```text
1 1 1 1 1 0.1 | data
```

直接使用输入十进制文本的候选会得到 `0.10`，因此更新的字符串不同。不能仅检查金额数值或客户返回字段，就忽略 C_DATA 这个持久化消费者。

### 3. 字符串长度语义不能按样本字符集推断

原 Java `substring` 按 UTF-16 代码单元计算下标。本轮用一个非 BMP 字符检验两种直接替换：

- C_DATA 拼接后截取 500 个 UTF-16 单元，实际得到 499 个 Unicode 码点，以 `😀` 结尾；取 500 个码点的候选还会保留后面的 `Z`。
- 仓库名 `aaaaaaaa😀Z` 经原方法截断后，历史数据中的仓库名为 `aaaaaaaa😀`；按十个码点截断会保留 `Z`。

两个例子都保留完整字符，没有依赖孤立代理项的驱动编码行为。它们证明两种截断定义不同，不是完整 PostgreSQL 字符串后端实现的测试。不能因为原固定数据目前没有这些字符，就缩小允许的数据域。

## 验证结果与范围

固定 16 项检查涵盖源码绑定、全部 SQL 支持、反射参数、分支双臂保留、未知阻断、读写依赖及实际探针。普通信用三次执行各记录八次 JDBC execute，坏信用两次执行各九次，符合实际分支路径。

本轮还用未修改的通用分析器重新生成上一轮 NewOrder 图，结果与归档完全一致。44 项原运行资产在测试前后通过哈希校验。原应用继续使用原执行路径，无数据、方法、SQL 或数据库机制删减。

第一次运行的十三项静态检查已通过，但探针替身没有实现结果投影所用的 `PreparedStatement.setObject`，因此在实际适配器调用处停止。补齐该已存在的 JDBC 边界后按同一协议执行五个用例；没有扩大数据或改变生产代码。失败归档保留。

本轮没有完整数据库回放、持久化结果比较、事务回滚、故障或并发验证；不能把五次边界执行计为五次真实数据库事务，也没有 Payment 加速结论。
