# 固定输入与顺序的事务回放

2026-11-03，按用户要求固定查询执行顺序或种子。已完成两次独立数据库恢复与串行回放，结果一致。此前四终端的随机混合负载保留为并发功能测试；本轮建立确定性参考基线。

## 固定了哪些条件

1. **初始状态**：两次都从同一个 `initial.dump` 恢复到新数据库，运行前核验快照 SHA256。没有重新随机装载数据。
2. **事务顺序**：[replay-schedule.json](../prototype/tpcc/replay-schedule.json) 数组定义全局次序。每笔事务提交或回滚之后才启动下一笔；四条连接按清单轮流使用，当前没有并发交错。
3. **随机输入**：十笔正常事务各自有固定种子（4200–4209），调用固定版本原始事务的输入生成器；另外一笔 NewOrder 直接指定最后一个商品无效。所有实际 JDBC 绑定参数也保存下来。
4. **写入时间**：每笔事务有固定 `clock_ms`，JVM 和数据库均使用 UTC。测试代理只替换已核查的三处 JDBC 时间绑定：订单创建、支付历史、订单行配送。未知的时间绑定会失败。业务源码未修改，但这是明确注入测试时间的执行环境，不是未经干预的生产时钟。
5. **程序版本**：沿用固定 BenchBase commit、PostgreSQL 镜像和分发包；执行前核验原始分发包及解压后全部 JAR。源码、配置和脚本的运行时哈希及快照归档。

事务清单是“NewOrder → Payment → OrderStatus → Delivery → StockLevel → 无效商品 NewOrder → 再执行五类事务”。测试驱动拥有提交/回滚边界，调用原版事务过程，绕过随机 Worker 调度。十笔正常事务使用原输入生成器；目前尚未把这些种子展开成独立于 Java/BenchBase 的完整业务命令格式。

运行标识 `7e3eaafec61d`。每次 11 笔事务：10 次提交、1 次预期中止，五类事务各成功两次。

- 两次初始状态一致，九张表均核对行数和全行摘要。
- 每次记录 **2,156 条 JDBC 操作及读回事件**，包括 SQL、绑定参数、批处理、实际读取值及提交/回滚，顺序和值完全一致。这个数字不是 SQL 条数。
- 最终九张表的全行摘要一致，包括所有时间字段；摘要算法为完整行 JSONB 的 SHA256，再对排序后的行摘要序列计算 SHA256，并另存行数。

- 两次的五项数据一致性检查均通过；独立容器、数据卷、网络清理完成。
- 40 项本地工具测试通过，其中新增 7 项回放比较测试。负例证明改变事务顺序、查询顺序、绑定参数、时间、读回值或最终状态会被拒绝。

## 后续使用边界

固定种子只能固定输入生成过程。固定初始数据、时钟和调度后，本案例才达到了重复运行一致。这里验证的是有限清单在固定参考实现上的确定性；未证明任意负载可确定重放，也没有测性能或完成 REA 副本。

下一步以这份固定清单为参考，为候选复现实现提取业务输入、结果及状态差量。候选能力验收以这些业务结果为准。SQL 次序精确比较用于确认参考基线自身稳定，不把相同内部 SQL 结构作为未来能力复现的必要条件。

如果后续需要可重复的并发冲突，需另行记录并控制事务间的关键交错点；当前串行回放不覆盖锁等待、死锁或序列化冲突的复现。先保留这个稳定起点，再讨论并发调度方案。
