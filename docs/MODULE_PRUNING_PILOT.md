# 反编译后按应用能力删减模块：单模块验证

2026-11-04。主线回到：**从反编译产物识别应用不需要的功能模块，删除其执行路径和依赖，同时保留明确约定的能力。** 缓存、SQL 计划选择和索引调优暂停。此次只做一个人工选定模块的小验证，不建立通用优化器。

后续已完成[删除条件与有限需求模型](MODULE_DELETION_CONDITIONS.md)，未改变本轮原始实验或扩展性能测量。

## 选中了什么，为什么可以讨论删除

对象是归档中由 Vineflower 反编译、重新编译并运行过的 BenchBase `OrderStatus`，不是把手写候选当作反编译结果。REA 在此前流程中提供制品取证；本轮没有新运行 REA 或声称它自动发现模块。

既有应用适配器的 OrderStatus 分支执行：

```text
客户读取/存在检查 → 最新订单选择
                       ↓
             getOrderLines：查明细 → 格式化为 List<String>
                       ↓ 返回值被适配器丢弃
             订单头查询 + 有序明细查询 → 完整 JSON 响应
```

选定模块为 `getOrderLines` 方法及专属 `ordStatGetOrderLinesSQL` 定义：职责是读取并格式化终端展示明细。粒度大于单个分支、小于整个 OrderStatus 类，具有明确输入、返回值、SQL 读取及异常边界。客户、订单、明细数据仍然全部保留；这里不按测试命中的记录裁剪数据。

有两个消费者必须区分：

| 入口 | 对模块结果的需求 | 判定 |
|---|---|---|
| 现有应用 `TpccApp.reference` 的 OrderStatus 分支 | 丢弃字符串列表，另行构造 JSON | 可提出受限删除候选 |
| 原 BenchBase `OrderStatus.run` | 终端 TRACE 展示会消费字符串列表 | 保留该入口能力时不能删模块 |

现有独立重构版已经手工省略了这条调用。此次贡献是把这项省略落实为**从反编译产物出发的明确删减及边界验证**，不是声称发现了此前不存在的性能优化，也没有证明比现有独立候选更快。

## 能力范围与条件化论证

保留的是应用适配器按客户 ID 查询订单状态的能力：完整订单头、按行号排序的全部明细、客户缺失与无订单错误、数据库状态不变。数据库内容不限于计时样本中的三个客户；数据是参数，方法的删除理由来自依赖关系。

本轮限定串行、同一固定快照、正常 JDBC/格式化完成、查询没有外部可观察副作用。诊断日志、数据库查询审计、反射枚举结果及原 BenchBase 终端入口不属于保留观察。并发、资源耗尽和任意故障等价不在该条件内。不是将早期 B1 的正常执行豁免自动搬到这里，而是对本次候选单独声明并保存故障反例。

记程序为 `A; m; B`，模块为 m，保留观察为 O。在以下充分条件下，才能把它改为 `A; B`：

1. m 的返回值、内存写入不进入 O 或 B 的数据/控制依赖；其他保留入口也没有需求。
2. m 不产生 O 所需的数据库写入、日志、锁语义等效果；内部资源正常释放。
3. 在约定环境内 m 正常终止，不通过异常改变后续行为。
4. 删除 m 及其专属依赖不破坏其他模块的初始化、调用或解析。

在这些条件下，m 对 B 所依赖的状态是恒等变换，且没有保留输出，因此删除保持 O。这是条件化的手工推理，不是从 8 个测试推导全输入等价，也不是机器证明。异常、反射和 SQL 效果的自动摘要尚未实现。

本例映射：字符串列表、StringBuilder 均为局部；传入 Customer 只在空明细的诊断文本中读取；SQL 是对 order_line 的普通 SELECT；后续完整响应由独立查询生成。框架按反射扫描 SQLStmt 字段，因此字段删除也会改变内部注册表和诊断信息；这些变化必须纳入依赖检查，不能只搜索 Java 的直接调用。

## 实际变换与固定实验

- 从哈希核验后的反编译 `OrderStatus.java` 删除方法和专属 SQLStmt 字段；从冻结适配器源码删除该调用。其余保留查询没有重写，没有增加缓存或索引。
- 原 BenchBase `run` 是被排除的入口，替换为显式拒绝的桩，避免删除后仍留下隐式使用展示模块的入口。这不是可直接替换完整 BenchBase 的版本。
- 特化后的 class 替换隔离 JAR 内的原 class。运行时检查实际类加载来源，确认方法和查询字段均已不存在，而非仅靠条件跳过。原归档和正式应用不改。
- 固定画像检查 5 项：声明范围接受；额外展示消费者、要求查询故障等价、观察读效果、未知上下文均拒绝。这是对人工声明的策略检查，不是自动发现或验证环境事实，也未接入生产分派器。
- 复用冻结数据库快照，在专用 PostgreSQL 容器运行。3 个预先固定客户场景，每臂预热 5 次，30 个随机顺序区块，顺序种子 20261104，共 180 个计时样本。

两臂使用相同数据、索引、JVM、连接与快照。计时包含整个适配器分支、过程初始化、保留查询和完整 JSON 渲染；不含连接/事务建立与提交、夹具、状态校验和诊断代理。这里是同进程热态的局部流程成本，非 TPC-C 吞吐或生产端到端时延。

## 结果

**8 组语义对照均一致，180 个计时样本均保持完整响应一致。** 语义用例包括 3 个已有客户，空明细、NULL 配送时间、非 NULL 配送时间且商品重复、客户缺失、无订单。后两者保留原异常类及消息。边界夹具在可写事务中构造，业务调用仍只有读取，随后回滚；正常对照和计时使用 SERIALIZABLE 只读事务。完整九表行摘要在实验前后不变。

独立诊断确认业务读取 **5 → 4**。这是删掉一个不服务于保留输出的计算模块产生的工作量减少，没有用更强 SQL 替换原查询。

| 地区 / 客户 | 原版中位耗时 ms | 删减版中位耗时 ms | 耗时下降 |
|---|---:|---:|---:|
| 1 / 1 | 2.108 | 1.680 | 20.3% |
| 1 / 2 | 1.999 | 1.565 | 21.7% |
| 2 / 1 | 1.687 | 1.383 | 18.0% |

每格 30 次调用，仅是一次本机运行的描述性结果，不能推广为任意数据下的加速保证。删除范围还包含专属 SQLStmt 初始化；未分项测定 SQL、字符串生成、初始化各自贡献，也不把静态代码体积减少本身解释为运行收益。

**保留了实际执行的异常反例。** 通过 JDBC 代理只让展示模块的那条查询抛出 SQLException：原版返回错误，删减版正常返回 JSON。因此“返回值丢弃 ⇒ 任意环境都可删”的规则被否定。故障用例不计入等价通过项或性能样本。

“额外展示消费者则拒绝”是策略测试与静态消费者事实，未伪装成另一次完整 BenchBase 运行。未知环境保持未准入；本轮实验成功不授权将删减版直接用于正式应用。

## 难点与停止点

这次支持一个有限结论：**应用能力之外的模块，即便原来每次都执行，也可以在明确条件下移除，并得到实际工作量与耗时下降。** 这比按覆盖率删除未执行代码更贴近项目目标。

待研究的核心是模块级的需求与效果依赖分析：从反编译程序及应用入口推导保留闭包，找到可整体移除的职责区域，并对异常、反射和数据库效果给出可核验的条件。普通死代码删除和程序切片本身不是新贡献；本轮人工绑定还不足以证明方法的新颖性或通用性。

本轮到此停止，不增加模块、场景或性能调优。接下来应讨论如何表达上述删减条件与模块粒度，而非继续优化缓存或选择器。
