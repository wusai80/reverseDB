# 候选相对变化的跨模块评分实测

2026-11-06。使用Payment、Delivery的6个候选实测标签拟合一次，再冻结对OrderStatus和StockLevel的5个目标候选的预测，最后运行目标验证。原版加11个候选，各34条固定请求，共408条全部完成。

**有局部跨模块排序信号，但尚不能可靠判断删减或改写。** 可评分目标的Brier比训练先验略好，固定0.5阈值仍漏掉唯一可评分的错误候选；另一个实际有错的StockLevel候选因表示不支持而弃权。

## 实验与冻结顺序

只用既有transaction_edges（27条）和delivery_edges（7条），每个场景／版本独立恢复完整初始转储，九表基础数据599,051行，输入顺序和时钟不变。每版30次提交、4次入口拒绝，无进程失败、业务中止或未执行后缀。本批标签属于34条协议，不能与此前70条协议标签直接混为同一批次。

候选只修改反编译类中选定SQLStmt的SQL文本，不改其他Java代码。新编译类实际加载；重新提取AST，核对全部JDBC绑定、其他SQL及候选SQL与预期一致；运行轨迹确认选定SQL确实执行。原版完整产物与此前独立归档一致。候选使用隔离类目录，默认应用未改。

先冻结候选、特征、提取器和模型设置，执行6个开发候选后拟合一次；将训练行、系数、特征取值和所有目标预测写入`before-target-predictions.json`，才开始执行目标。最终核验该预测文件及冻结输入哈希未改变。

## 共同特征与模型

沿用上一轮冻结的SQL值／效果IR，不补SQL解析规则。比较同一语句原版与候选，得到六项数值：

- 写入／投影值结构改变比例。
- 行选择表达式是否改变。
- 排序结构是否改变。
- 数量限制是否改变。
- 参数使用次数变化。
- 数字字面量总和的绝对变化量。

最后一项只是语法数值摘要，不代表业务金额或语义距离。标识符用于原版／候选对应，不把业务模块名、表名或参数槽位号作为学习特征。无法表示整条SQL或对应关系不成立时弃权，不填零。

复用既有带L2正则的逻辑回归：每个开发模块总权重为1，训练集中心化，截距固定为训练数据Beta(1,1)平滑先验，λ=1，诊断阈值0.5。没有系数方向规则、特征搜索、阈值搜索或后续调参。训练先验为0.416667。

这是“同一Java代码、单SQL改写”条件下的结构评分：Java中原有未知值仍未知，相同Java源代码也不保证修改SQL后得到相同运行时值。本轮没有把它升级为整个模块的能力评分或删除概率。

## 冻结目标预测与随后得到的结果

| 目标候选 | 冻结分数 | 实测差异标签 | 结果 |
| --- | ---: | ---: | --- |
| OrderStatus原样重编译 | 0.3963 | 0 | 完整观察一致 |
| OrderStatus选择参数加入`+0` | 0.3734 | 0 | 完整观察一致 |
| OrderStatus排序DESC改ASC | 0.4480 | 1 | 返回改变，最终九表相同；0.5阈值漏判 |
| OrderStatus LIMIT 1改2 | 0.4462 | 0 | 本批完整观察一致 |
| StockLevel阈值`<`改`<=` | 弃权 | 1 | 多表SQL不支持；仍实际执行并发现返回差异 |

具体见证：

- OrderStatus的edge-18：原版返回订单3001，排序反转版返回2776。两个场景组都有响应差异，九表最终状态和逐请求状态观察一致。
- StockLevel的edge-19：原版低库存计数0，候选为3；delivery_edges的edge-07为0与1。弃权不是安全，也没有将这例从总候选数中隐藏。
- LIMIT 2的查询实际执行了4次，完整观察均一致。事后检查源码可见`getOrderDetails`只`next()`一次，读取首行后返回，未消费第二行。此解释未回流为特征或改写安全规则。

同一可评分集合的指标如下：

| 指标 | 训练先验 | 冻结模型 |
| --- | ---: | ---: |
| Brier | 0.215278 | 0.200093 |
| Log loss | 0.623115 | 0.591558 |
| 阈值0.5漏判 | 1 | 1 |
| 阈值0.5误报 | 0 | 0 |

目标评分覆盖4/5；这4个都属于OrderStatus，StockLevel没有可评分候选，不能称为两个目标模块都成功迁移。排序错误的分数略高于其余三个，但与无差异的LIMIT候选仅相差约0.00176，不足以支持可靠选择。训练中的`limit_changed`恒为0，其系数为0；LIMIT候选的新取值已单独记录，分数主要受数字字面量变化的既有权重影响。

## 收敛后的难点

现在不是简单缺少一个更好的阈值。关系表示仍停在SQL输出端，没有继续连接ResultSet读取方式、Java值传播和应用最终结果：

`SQL投影／排序／数量限制 → ResultSet实际消费 → Java返回值 → 应用观察`

本例中排序改变了被消费的首行，而LIMIT增加的第二行没有被消费。当前粗粒度特征尚不能表示这个区别。这是后续应研究的通用跨层消费关系，不能写成“LIMIT变大安全”之类的业务规则，也不能因为某些数据本次未消费就删除数据库数据。

本批到此结束，保留漏判和弃权，不调权重／阈值，不追加样本。下一阶段若使用这些结果改进表示，这些目标已成为开发材料，需要另外安排评估目标。没有性能提升或实际模块删减的结论。

## 证据质量与限制

比较完整响应、逐请求观察、九表完整行哈希及初始状态，检查提交／回滚轨迹和实际候选SQL执行。保留SERIALIZABLE、WAL、fsync、同步提交和全页写入。8项特征控制、9项时间追踪器检查通过；859个归档文件哈希核验，容器和卷清理后额外只读确认无残留。

这是单项目、已见模块与固定场景上的小型开发实验。候选人工选择，原样、零变化和错误改写互相关联，排序等变换机制跨训练与目标复用；前三个OrderStatus特征向量也在开发候选中出现过。因此不能把Brier小幅改善称为独立泛化证明或概率校准，更不能按请求数量宣称408个独立学习样本。
