# 融合区域与阶段依赖：第一轮静态验证

2026-11-05。本轮完成一个保守的融合区域识别器，并接入现有 NewOrder 生成入口。算法以已知语义单元为输入，自动分析受支持 SQL 的读写效果、构造依赖边、划分连续数据库候选区域；未自动恢复任意 Java 程序的循环或副作用。

后续已完成[第二类事务 Payment 的迁移审查](PAYMENT_FUSION_TRANSFER.md)。通用算法未改；SQL 效果可复用，金额、对象与字符串语义仍阻止整段下推。下文保留本轮的验证边界。

NewOrder 的 12 个内部阶段被归入一个区域，覆盖 13 处静态 SQL；输入验证及提交／回滚仍在区域外。27 项固定检查通过。生成的四种 SQL、来源映射、外层辅助类和适配器与上一轮已验证产物一致，本轮没有新增数据库执行或计时，也没有新的加速百分比。

## 解决的问题与输入边界

上一轮已经验证将完整事务移入数据库能够减少跨进程调用，但融合哪些阶段、为何不能调整顺序仍主要由人决定。本轮把这部分决定表达成可检查的区域与依赖模型。

输入是按源码顺序排列的语义单元，每个单元包含 SQL、所属事务、必要输入值、定义的值、业务检查、后端位置与已知效果标记。NewOrder 的 SQL 和顺序来自既有提取结果；阶段分组、值类型、异常摘要和 `body_known` 标记由绑定源码哈希的人工规则提供。不能把这个已知标记当成工具自动证明了方法体没有其他副作用。

例如，`stage_lines` 是“按输入顺序读取并暂存**全部**订单行”的一个阶段，随后才有 `flush_lines` 和 `flush_stock`。这是从上一轮已核验程序引入的阶段契约，不是本轮重新发现的循环结构。

## 区域判定与依赖

设源码中的有序单元为 `u₁ … uₙ`。当前算法只考虑连续区间 `R = [uᵢ … uⱼ]`。候选必须满足：

1. 所有单元都可在数据库后端执行，所属事务相同。
2. 方法体效果已由前端摘要覆盖，SQL 属于受支持语法，值的生产者与表示已知。
3. 区间不跨过应用端操作、未知调用或事务边界；完整保留区间内的阶段及源码顺序。

扫描得到满足条件的最大连续区间，同时计算区域的输入和输出值。这里的“最大”只指不能再向相邻单元延伸，不表示成本全局最优。区域仍是候选：跨区域值的实际序列化、模式约束、异常与类型语义必须由执行后端履行。当前 NewOrder 后端只接收一个完整内部区域，不支持自动拼装部分区域或自动回退。

依赖分析对每对有序单元保守建边：

| 依赖 | 保留的义务 |
| --- | --- |
| 值流 | 先产生订单号、暂存明细等值，再消费 |
| 写后读、读后写、写后写 | 保留同表读写的可见顺序 |
| 锁顺序 | 保留显式锁及写操作的既有顺序 |
| 写入顺序 | 不假定不同表因表名不同就独立；模式约束可能关联它们 |
| 控制守卫 | 先通过业务检查，再进入后续阶段 |
| 源码顺序 | 本轮只改变执行位置，不授权阶段重排 |

读写冲突按**表级可能别名**判定。不会因为样本中的商品 ID 不同，就判断两次库存访问永远互不相关；不会删除任何数据。SQL 效果提取只支持简单单表 SELECT、可选 FOR UPDATE、简单 UPDATE 和 INSERT。函数调用、JOIN、子查询、CTE、事务指令等均返回 unknown；语法白名单之外的表达式不会被当作纯读取。

建图复杂度为单元数的平方，区域扫描为线性。当前实现是简单保守划分，不是新的最优调度算法或完整 SQL 语义分析器。触发器、外键副作用等仍依赖上一轮的冻结模式与执行契约。

## 库存反例如何变成生成前的拒绝理由

用 `begin(u)` 和 `end(u)` 表示整个阶段的开始与完成，包含该阶段的所有输入循环迭代。依赖边要求：

`end(stage_lines) < begin(flush_stock)`

理由包括 stock 表的读后写依赖，以及暂存明细尚未完全产生。错误候选把 `begin(flush_stock)` 放在 `end(stage_lines)` 之前，检查器会在生成正常候选前拒绝它，并列出对应依赖。

这与上一轮真实数据库反例相对应：重复商品用例中，原版库存数量为 76，错误提前写入为 75。本轮直接引用并校验该已有见证，没有再次执行，也没有把具体商品或库存值写进判定规则。

阶段事件来自候选计划的声明，不是对任意输出 SQL 的独立验证。后端正确性仍依赖人工核验与既有差分证据。当前生成器不实现任意计划调度，接受的计划须保持固定完整阶段布局；检查通过不构成一般程序等价证明。

## 实现与本轮验证

- [区域与依赖实现](../scripts/fusion_regions.py)：受限 SQL 效果提取、通用区域扫描、阶段计划检查，以及 NewOrder 专用前端摘要。
- [生成器](../scripts/generate_neworder_fusion.py)：正常 `full`、`pruned` 生成入口先检查完整区域和阶段计划。
- [静态实验](../scripts/test_fusion_regions.py)：固定负面控制及与既有后端的产物比较。
- [原数据库实验驱动](../scripts/test_neworder_fusion.py)：未来执行时会保存区域计划并冻结新增依赖；本轮只做语法与产物检查，没有启动它。

`pruned` 的仓库检查删除仍沿用上一轮单独的外键契约，本轮区域分析没有新增删除授权。`early_write`、`full_fault` 两个故意错误／故障注入模式仍是显式测试控制，绕过正常候选计划检查；不能作为被批准的优化计划。

最终固定检查共 27 项，其中包括两个明确矩阵：11 种内部相邻阶段换序全部拒绝，11 种不支持的 SQL 形式全部保持 unknown。其他检查覆盖：

- 正常阶段接受；提前写入、漏阶段、重复阶段和未见节点拒绝。
- SQL 未知时切断区域，现有完整事务后端拒绝部分融合。
- 没有 SQL 字符串的未知回调仍是屏障；已知但在应用端执行的回调也不能跨过。
- 不合并不同事务；未知值表示、缺失生产者、重名节点和值定义拒绝。
- 更换表名为 inventory 后仍识别读后写依赖，说明通用判定不依赖 stock 这个名称；这只是结构夹具，不是第二个真实应用验证。
- 从冻结源码与提取事实重新得到相同中间表示；四种 SQL 字节相同、来源映射值相同，外层 Java 辅助类与适配器字节相同。

最终图共 14 个节点（12 个内部阶段与两个外部边界）、113 条带理由的边。边数包括源码顺序及多个理由，不等于 113 项相互独立的证明。所有 499 个上一轮归档文件通过哈希核验。

首次静态运行在 IR 比较处停止：内存中的地区映射用 tuple 表示，JSON 归档用数组表示。修正为相同 JSON 表示后执行上述固定检查；未改业务语义或放宽判定，失败归档保留。没有为改善结果追加数据集或计时。
