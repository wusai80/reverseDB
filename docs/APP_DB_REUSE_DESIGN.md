# 从单次查询到应用流程：缓存、复用与索引选择

2026-11-04。用户提出进一步考虑内存缓存、结果复用和索引。将其作为现有 P1/P2 的候选实现与成本选择维度，明确语义条件及后续最小实验。本轮为设计更新，没有实现缓存、创建新索引或启动另一轮性能测试。

**后续进展：** 用户授权后完成[固定双消费者实验](APP_DB_WORKFLOW_REUSE_RESULTS.md)。结果共享、预算和生命周期通过受限语义验证；应用缓存没有胜过最快基线，简单成本模型及在线选择开销暴露了新的难点。下文保留设计时的边界，不表示跨请求缓存或索引选择已实施。

## 1. 目标调整与公平比较

[上一轮实验](APP_DB_COST_RESULTS.md)比较的是单次、独立的夹具调用。常规 SQL 强基线在该范围内更快；这不说明它已经优化了整个应用流程，也不保证加入缓存后我们一定更快。

新的候选目标是：在应用流程的多个消费者、明确的结果有效期和共同资源预算下，选择计算位置、物化/复用方式及索引，使整个流程成本降低。

常规手工方案也允许使用相同内存、结果共享、相同候选索引与一致性契约。比较以下两个问题应分别报告：

1. 相对逐调用独立优化，利用流程信息是否有价值？
2. 相对拥有相同流程信息与资源的手工共享方案，自动识别/选择能否接近或超过其成本，或者减少人工义务？

第一个问题通过不等于第二个问题通过。若离线候选搜索空间包含手工方案，应报告选中了它；“手写”与“自动”本身不是可证明的性能上下界。

上一轮所有方法已共同使用 targets、links、allowed 的相同索引，因此不能把此前结论解释为“普通 SQL 没有索引”。后续研究索引选择时，候选集合、存储预算与建设成本须对所有方案一致。

## 2. 三种机制的区别

| 机制 | 可选择对象 | 核心语义义务 | 必须计入的成本 |
|---|---|---|---|
| 单流程结果复用 | 多个消费者共享同一或覆盖其需求的中间关系 | 输入、参数、权限、类型、快照及效果兼容；派生结果足以回答各消费者 | 首次计算、物化、读取/传输、额外计算域、清理 |
| 内存结果缓存 | 中间关系保存在应用内存及其生命周期 | 复用义务加生命周期有效性；跨请求还需数据/权限变化后失效或刷新 | 未命中、验证、建立、命中、失效/刷新、淘汰与占用 |
| 索引选择 | 数据库基础关系或物化中间关系上的访问结构 | 不改变合法结果；所需顺序仍显式保持；部署约束满足 | 建设/存储、读成本、写入维护、必要锁与摊销 |

结果复用是逻辑选择，内存只是实现位置之一；也可在同一 SQL 或数据库临时关系中共享。二者不应被当作两份独立收益重复相加。一般索引不直接提供完整聚合结果，不能等同于结果缓存。

## 3. 工作负载上的形式定义

令 `W=(e1,…,eT)` 为具有明确顺序的应用事件，每个事件包含输入参数、身份与消费者；允许的事件族由 κ 给定。M_t 为时刻 t 可用的物化/缓存结果，I 为候选索引配置，Π 为各事件的执行计划及共享/淘汰策略。

总体问题写成：

```text
min  C_build(M0,I) + Σ_t C_event(et, Πt, Mt, I) + C_planning

s.t. ∀ W∈Wκ:
       Obs(original,W) = Obs(Π,M,I,W)
     Σ_{m live at t} size(m) ≤ B_memory        对所有 t
     Σ_{i selected} size(i) ≤ B_index
     每个复用结果在消费时满足 Valid(m,et,κ)
```

`C_event` 包含该事件实际执行、结果验证、缓存未命中/命中、失效/刷新、淘汰及写维护所需成本；计量时避免把已包含在数据库耗时中的索引维护再加一次。首次建立和最终清理不可只为候选放到计时之外。单次命中延迟与完整生命周期成本分开报告。

这里的等价量化约束针对事先限定的事件族，不意味着已经证明任意并发工作负载等价。首个实验仍只接纳一个只读固定快照流程，其他事件保留为未准入候选。

## 4. 可复用结果的身份与有效性

一个候选物化结果需要记录：

```text
语义区域/查询版本，实际参数，键域与字段，类型/顺序契约，
有效关系与权限上下文，数据有效期，效果约束，来源义务
```

这些信息首先用于判定是否可复用；并非写成一个哈希键就自动证明正确。相同 SQL 文本不保证同参数/权限，相同用户 ID 不保证权限未变化。

同一只读固定快照流程内，若两个消费者分别需要 `Δ1`、`Δ2` 的计数，可以研究一次计算 `G(Δ1∪Δ2)`，再分别投影/筛选。每个所需分组仍保留全部有效输入，输出行的重复和次序由各消费者保持。若各自过滤、允许文档集或类型语义不同，不能仅按相同 group key 合并。

跨请求有效性比“缓存命中”更强：插入新关联也能改变旧计数，即使以前读取的所有行都未更新；缓存零结果同样受影响。因此只比较已读行的版本，或仅设 TTL，都不足以证明严格结果一致。还需覆盖相关插入/删除、软删除、权限改变、schema/转换器变化，以及有效性检查到使用之间的竞态。没有这些机制时保持未准入，不给旧结果贴上新鲜标签。

首轮使用同一个 SERIALIZABLE 只读事务、相同连接上下文和无相关自写入；排除 volatile 表达式及未建模副作用，并在事务结束销毁全部可复用结果。仅声明“同一事务”仍不够，READ COMMITTED 的多语句快照差异不能被忽略。

## 5. 与 AND–OR 图及背包模型的对应

在[原模型](APP_DB_THEORETICAL_MODEL.md)上扩展合法候选边：重新计算、数据库内共享、应用内存物化后读取，以及利用指定索引的访问路径。节点身份包含需求和有效期，两个消费者能否合并节点由语义条件决定。

物化节点的建设成本只计一次；多个读取边各有读取/传输成本。其收益取决于复用次数、需求重叠、首次建设量、内存占用以及有效期。索引也会改变共享与重算的相对成本，二者的收益通常不能独立相加。

在候选结果彼此独立、收益可加、生命周期固定时，内存/存储选择可以退化为背包或多维背包。一般情况使用带依赖、共享与生命周期资源约束的计划选择，不把某一必需业务输出当作可丢弃物品。

这给原来的“缩减”增加了重要的成本条件：**每个消费者单独只算最小域，不一定使流程总成本最低。** 计算一次稍大的需求并集，再供多个消费者使用，可能优于多次计算小域；也可能因传输或物化更贵而失败。应由完整成本和语义条件决定。

## 6. 建议的下一个最小实验

优先验证**同一只读流程内的多消费者结果复用**，暂不同时实现跨请求失效或自动索引建议。这与已验证的单生产者关系、类型和固定快照最接近，也能直接检验共享成本模型。

固定一个包含两个计数消费者的流程，预先声明各自的过滤、顺序、分页和需求键关系；覆盖需求无重叠、部分重叠、完全相同三种情况。键关系由输入计算，不把采样 ID 写入规则。两端同时得到整个流程描述，不允许只有候选预知后续请求。

比较四类候选：

1. 每个消费者独立执行已知强 SQL。
2. 手工工作流级 SQL 共享：一次求需求并集，在数据库内产生两个完整结果。
3. 共享中间关系后在应用内存分别满足两个消费者。
4. 受限选择器在相同候选、信息与资源预算中作选择。

先做语义验证及预算不足时的重算回退；然后才比较包含建立/释放的整段流程成本。数据、索引与原执行顺序固定，内存不足不能少返回数据。内存计量需针对本轮结构给出可审计的占用定义，不能继续把旧实验中分辨不足的堆增量 0 当成免费缓存。

这只是下一步实验设计，尚未执行。若内存共享输给数据库共享，也保留结论；不追加更多消费者或缩窄基线来制造优势。跨请求缓存与索引选择作为后续独立候选，须先补齐各自有效性与维护成本契约。

## 7. 潜在研究贡献的位置

缓存、共享、索引及背包求解本身都不能直接视为创新。待验证的是：能否从应用/反编译得到的跨层依赖和消费者条件中，恢复可共享的计算区域、有效期与需求范围，进而在同等资源下选择合适的重算/共享/访问路径，并对未知条件保守拒绝。

本设计没有证明能够击败拥有相同信息的专家方案；目标是建立可检验的识别、正确性和选择机制，而不是通过给候选更多资源获得不对等比较。
