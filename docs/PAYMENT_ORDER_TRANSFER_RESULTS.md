# Payment迁移验证：顺序特征有用，但看不到条件错位

2026-11-06。完成真实Payment候选的固定端到端验证。**原有顺序关系特征能区分合法换序与提前读取旧余额，但正常版本和信用条件反转版本具有相同特征、不同执行结果。** 因此不能只靠增加当前模型的权重或调阈值解决条件依赖问题。

本轮复用 `real_order_features.py`，没有修改提取算法、拟合模型或迁移小模型系数。这里检验的是关系表示的跨模块适用性，不是已训练模型的泛化分数；Payment与NewOrder仍来自同一项目，且候选是有意选择的语义对照。

## 执行前固定的四个候选

原版作为独立对照。四个候选共享已修复的Java时间绑定、原金额运算、同一NewOrder融合和全部数据库数据，只替换 `finish_payment` 的SQL函数体：

| 候选 | 变换 | 顺序反转对数 | 潜在同表冲突对数 |
| --- | --- | ---: | ---: |
| 正常融合 | 保留顺序与信用条件 | 0 | 0 |
| 合法换序 | 交换历史写入与客户结果读取 | 1 | 0 |
| 提前读取 | 把结果读取移到余额更新之前 | 3 | 2 |
| 条件反转 | `IF p_bad`改为`IF NOT p_bad`，SQL排列不变 | 0 | 0 |

特征在数据库执行前保存。现有提取器不表达IF谓词，两个互斥的客户更新分支作为可能效果保留；表中2对冲突是可能关系，不表示两个分支在一次请求中同时执行。运行时逐字节核验安装函数体，执行后再次提取的特征与事前记录相同。

## 同一固定协议的结果

沿用五组场景、70条顺序固定的请求，包含五种事务、GC／BC信用分支、不同付款／客户地区、极大时间、业务中止及输入拒绝。每版每场景从完整快照恢复，保留全部599,051行初始数据及场景夹具。实际经过应用入口、JDBC和提交／回滚；对照完整响应、逐请求观察及进程退出后的九表完整行数／哈希。

| 版本 | 实际尝试 | 完成 | 应用异常 | 与原版差异 |
| --- | ---: | ---: | ---: | --- |
| 原版 | 70 | 70 | 0 | 基线 |
| 正常融合 | 70 | 70 | 0 | 全部一致 |
| 合法换序 | 70 | 70 | 0 | 全部一致 |
| 提前读取 | 70 | 70 | 0 | 四组场景返回旧值；观察和最终九表仍一致 |
| 条件反转 | 34 | 30 | 4 | 四组场景因非空约束错误退出；36条后续请求未执行 |

最终一轮350条预定请求中，实际尝试314条、完成310条、失败4条、未执行36条。完成包括正常提交、业务中止和输入拒绝。前四版均为56次提交、5次业务中止、9次拒绝。不能把提前退出算作完成70条，也不能将截断序列的最终状态与完整序列相比后归因于某一字段写错。

合法换序支持的条件仍是固定串行环境、完整原模式、正常查询完成及不要求SQL轨迹相同。本轮的错误均由候选在原版可正常提交的合法请求上制造，不是外部故障注入；不能用“正常执行基线”将它们排除。

## 两类反例

### 结果错误，最终状态正确

baseline的 `tx-02` 在原版返回客户余额 `-2954.67`、累计付款 `2954.669921875`、付款次数2；提前读取版本返回更新前的 `-10`、10、1。真正的余额更新仍发生，完整九表最终与原版一致。

因此仅检查数据库最终状态也会漏掉错误。必须同时保留返回值观察和完整状态观察。这个错误与NewOrder提前写库存相反：前者是读取了旧结果，后者是提交了错误库存；同一种读写顺序关系在两个模块中均提供了区分信息。

### 条件错位，使用了未准备的值

Java helper只在坏信用条件 `bad` 成立时，调用原 `getCData` 并准备新的 `cust.c_data`。普通信用路径不需要该值，传给SQL的 `p_data` 可为null；数据库中的完整原记录仍然保留，并非删除了业务数据。

原SQL也只在 `p_bad` 成立时写 `C_DATA`。反转SQL条件后，普通信用请求进入了使用该值的分支。实际追踪显示：

```text
setString(8, null)       → p_data
setBoolean(9, false)     → p_bad
IF NOT p_bad            → 执行包含 C_DATA = p_data 的更新
NOT NULL约束异常        → rollback，应用退出
```

原版对相同请求成功提交。最终一轮的失败请求分别为baseline `tx-02`、holdout `new-10`、transaction_edges `edge-13`、time_boundaries `edge-pay-gc`。配送场景完整完成且一致。

这揭示的是跨Java／SQL的条件化值依赖：**准备值的条件与使用值的条件必须对应**。SQL调用关系、语句集合与顺序全部保持不变，仍可能破坏应用能力。

## 对概率模型的含义

在本批观察标签下，存在：

`φ(正常融合) = φ(条件反转)`，而 `y(正常融合)=0`、`y(条件反转)=1`。

任何只使用当前特征向量的确定性评分函数都会给两者相同分数，无法分别识别这两个结果。这里的0只表示指定验证批次未发现差异；这个特征碰撞结论限于本批记录，不宣称一般程序的不可能性。

下一项值得研究的输入是“生产者条件—消费者条件—被使用的值／写入效果”的关系，而非再增加几个调用次数。它应成为可学习的特征和明确的未知信息，不直接手写成安全／危险判定规则。本轮不增加此特征后再回头重调同一批结果。

## 观察器修正与证据

首轮观察器默认应用会完成全部请求，因此在真实条件反转异常处停止。该轮实际尝试46条请求，保留于[首轮归档](../evidence/payment-order-e2e/20261106-f5ca843c3e37/run.json)，不计为额外独立样本。随后只修正观察器：记录指定负控的非零退出、失败请求、未执行后缀，并将截断状态标为不可与完整回放直接比较。

两轮10份生成代码／输入／特征产物逐字节一致；没有改变候选、请求、模型或特征以取得更好的结果。最终892个归档文件哈希已核验；两轮临时容器与卷均清理，并再次查询确认不存在。完整业务数据、事务机制和默认应用没有改动。
