# 条件化值依赖特征：分开准备条件与消费条件

2026-11-06。完成一条真实 Payment Java→JDBC→SQL 传值链的特征补充。**此前正常融合与信用条件反转具有相同顺序特征；加入条件化值关系后，两者不再具有相同向量。** 本轮没有训练新权重、生成风险概率或增加数据库执行。

## 特征定义

P表示选定的条件赋值是否执行，C表示SQL消费者是否执行。对Java原始布尔条件的两个符号取值分别求P、C，记录四种组合：

| 组合 | 含义 |
| --- | --- |
| C且非P | 消费发生，但选定的条件赋值未执行 |
| P且非C | 选定赋值执行，但该消费者不执行 |
| P且C | 两者均执行 |
| 非P且非C | 两者均不执行 |

每项数值是符合组合的符号取值数除以2。**这不是请求频率，也不是故障概率。** 没有假设真实GC／BC客户各占一半；没有从测试数据分布裁剪能力域。

P只描述选定赋值在正常完成情况下的执行条件，不证明所得值正确、非空或唯一。同一字段可能有更早的合法值或其他生产者，其可用性在这里尚未知。因此C且非P出现并不能直接判危险，数值为0也不能授权删减；这些是未来模型的输入。

## 实际传值链

在冻结 helper 中恢复选定单条件赋值 `if(bad) cust.c_data=...`，核对它位于绑定之前；读取 `setString(8,cust.c_data)` 和 `setBoolean(9,bad)`，再按目标函数形参位置连接到 `p_data`、`p_bad`。消费点是相应SQL分支内的 `C_DATA=p_data`。

原程序满足 `P=bad、C=bad`。条件反转候选为 `P=bad、C=not bad`。若JDBC布尔实参本身有逻辑否定，会在连接时组合该否定，而不是仅比较两个条件字符串的名称。

当前实现只处理这条预选链的原始布尔变量及单次否定。槽位8／9、正常finish调用及选定C_DATA消费者是显式范围；其关系来自源码和参数对应，没有读取历史标签生成特征。它不是全程序控制DAG恢复，不能推广到任意Java别名、嵌套条件、Nullable SQL布尔值或外部直接调用数据库函数。复合条件、重复绑定、布尔重赋值及不支持的表达式返回unknown，数值为null。

## 与已有顺序特征合并

| 候选 | 顺序反转 | 潜在同表冲突 | C且非P的符号比例 | 已有批次差异标签 |
| --- | ---: | ---: | ---: | ---: |
| 正常融合 | 0 | 0 | 0 | 0 |
| 合法历史／结果换序 | 1 | 0 | 0 | 0 |
| 提前读取余额 | 3 | 2 | 0 | 1 |
| 信用条件反转 | 0 | 0 | 0.5 | 1 |

这样，条件错位与读写重排分别保留了区分信息。对正常版本与合法换序，该关系的“共同执行／共同不执行”比例均为0.5；对条件反转，“消费但未赋值／赋值但未消费”比例均为0.5。

四个分量总和为1，并不是四份独立证据；将来建模需要处理这种冗余，不能以增加列数冒充增加样本。这里也未把比例线性加权成安全分数。

原失败调用中的 `p_data=null` 及非空约束错误仍以先前真实执行记录为依据；当前特征本身不推导null。上述标签继续表示既有固定协议是否发现差异，不是全能力标签。

## 固定检查与边界

12项检查通过，包含：

- 正常／条件反转的关系被分开，原顺序特征保持不变。
- Java与SQL关联变量改名不改变数值；注释中的伪造赋值不成为证据。
- JDBC实参否定与SQL条件否定正确组合；只否定生产者改变关系，同时否定生产者与消费者保持对齐。
- 复合生产条件、复合消费条件、重复数据绑定、布尔重赋值和不支持的布尔实参保留unknown。

“两端同时否定仍对齐”尤其说明特征不等于完整语义判据：两端一致仍可能改变业务应适用的信用分支，需要其他依赖及验证证据。本轮这些变换只用于静态提取控制，没有运行新业务或赋予新的安全标签。

特征快照在加载既有执行标签之前保存哈希。不过特征设计已经受已知反例启发，因此只能证明本批表示不再发生原来的碰撞，不能声称独立泛化或校准改善。
