## 如何确认真正执行了重建代码

1. 构建脚本按上一轮反编译 manifest 校验每个 Java 输出的 SHA256，再复制、编译；没有读取应用原始 Java 源码，也没有修补反编译输出。
2. 候选编译目录先仅放入冻结的公共框架，再从反编译输出生成五个 Service、Sql、CandidateApp 及嵌套类，共 10 个 class。禁用隐式源码编译，运行时只加入该目录及 JSON/PostgreSQL 两个依赖。
3. 参考端从反编译输出生成五个过程与 TPCCProcedure，共 6 个 class，替换固定 BenchBase JAR 中的同名成员。参考运行路径使用这个新 JAR，保留未选中的依赖类。
4. 所有目标的原始与重建字节码 SHA256 均有记录；本次 16 个目标的字节码摘要都发生变化。运行前后校验构建文件和依赖摘要，并用 JVM 类加载日志确认全部 16 类均从指定重建目录/JAR 加载。
5. 补充的严格核对将日志来源解析为文件 URI，要求路径精确相等，拒绝仅前缀相同的其他目录。原运行记录保留；该次独立复核另存为 `rebuild-class-binding-strict.json`。

反编译源由 Vineflower 1.12.0 产生；REA 的贡献仍是此前的制品身份取证，不能把这次 Java 反编译归因为 REA/JEB 自动恢复。

## 边界与下一步难点

这是**选定业务类的反编译—编译—运行闭环**，不是整个应用的无源码重建。AppRuntime、JdbcTrace、Observation、参考适配器、未选中的 BenchBase 类和第三方依赖都保留冻结字节码。事务边界及部分投影仍依赖这些框架。此前已经阅读源码，也不构成无源码盲测。

目前覆盖单仓库、按客户 ID、四连接串行清单。未证明多仓库、按姓氏、并发交错、数据库故障和全部输入域等价。没有做性能优化，诊断日志不能用于加速比结论。

本轮未出现需要修补反编译代码的业务反例。已确认的分析难点仍是**业务边界跨越类和运行框架**：例如 OrderStatus 的订单 ID 选择与订单行投影分属 Service 和入口层，提交/回滚位于共享框架。下一步应把输入、读写集合、状态变化、事务边界与对应证据整理成可检查契约，再以反例评估遗漏；是否扩大反编译范围、如何恢复跨类关系，需要以具体缺口讨论。此时不把工具串联视作核心创新。
