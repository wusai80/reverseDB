# 两个方法模块的组合删减

2026-11-05。上一轮新增的是一个方法级模块，而非整个类或数据库子系统。此前分别验证过姓名查询与订单明细展示两个候选；本轮首次把两项删减组合进同一个可运行版本，验证它们在已有应用的完整事务序列中能否共存。

| 模块 | 当前应用中的情况 | 本轮处理 |
|---|---|---|
| `OrderStatus.getCustomerByName` | 应用只按客户 ID 查询，此方法不可达 | 删除方法 |
| `OrderStatus.getOrderLines` | 被调用，但生成的终端展示字符串列表被丢弃 | 删除方法及适配器中的该调用 |
| 四个 `SQLStmt` 字段与初始化 | 框架反射注册，具有独立初始化边界 | 全部保留 |
| 客户检查、最新订单选择、完整订单及明细 JSON | 属于应用需要的能力 | 全部保留 |

这里的“两个模块”指两个具有独立职责和边界的方法，仍位于同一个 `OrderStatus` 类中。原终端 `run` 的拒绝桩是应用专用版本的入口处理，不计作第三项模块发现。没有删除整类、表、行、列或任何合法客户数据。

## 组合条件

令姓名删减为 (T_N)，展示删减为 (T_D)。组合版只在两项原有契约的交集下讨论：

\[
C_{ND}=C_N\cap C_D,
\qquad
O(T_D(T_N(P)),x)=O(P,x),\quad x\in C_{ND}.
\]

这是待满足的条件化正确性要求，不能由有限回放直接证明。当前依据包括人工源码与入口论证、构建验证、保留效果边界和固定反例测试，尚不是自动全程序证明。

关键条件为现有 `TpccApp.main` 入口、原有合法输入域、串行执行，以及被删除展示查询与格式化正常完成且没有额外可观察的读取效果。完整业务响应、其他业务错误和数据库状态是保留观察；原 BenchBase 终端、任意外部反射入口、诊断日志和 SQL 审计不属于此画像。故障等价不成立，不能把较宽的姓名查询删减结论直接转移给展示删减。

具体组合检查：

- 两个方法的删除区域不重叠。按姓名→展示或展示→姓名顺序生成的最终源码完全相同；此检查只说明这两个具体文本变换相容，不是一般语义可交换定理。
- 适配器仅删除原先丢弃展示返回值的一行调用，其余事务、客户/订单检查以及完整 JSON 查询不变。
- 与早期展示实验不同，本轮保留 `ordStatGetOrderLinesSQL` 字段。姓名 SQL 字段也保留，四项初始化注册内容在原版与组合版中完全一致。
- 修改后的类必须从新 JAR 加载，适配器必须从配套编译目录加载；两者的运行时来源均核对。其余 JAR 条目与原版逐字节一致。

## 固定验证

只比较原版与组合版，使用既有 baseline、holdout、transaction_edges、delivery_edges 四个冻结场景；每组 62 条命令，各场景独立恢复完整数据库。输入顺序、时钟、终端分配和已有场景设置不变。未重新调参、扩大样本或重复旧的单模块计时矩阵。

每个场景比较完整响应、逐命令业务观察、九张表初始与最终完整行哈希、五项一致性约束。JDBC 记录不能要求原样相等，因为预期要移除展示查询：按该查询的精确 SQL 识别连续参数绑定、执行和取行片段，保存被移除的原始事件，再要求其余所有事件与组合版逐项、逐序相同。投影规则只用于诊断，不能据此声称 SQL 审计观察也等价。

额外探针直接检查两个方法的存在性、四项 SQL 注册表、原终端拒绝行为和姓名能力的范围差异；对同一真实订单分别执行正常查询与展示查询故障注入。故障探针不修改业务数据。

固定验证已通过，完整结果见[运行记录](../evidence/module-combined-pruning/20261105-454cdefc9245/run.json)。原版与组合版共执行 **124 条应用命令**，每组均为 50 次提交、4 次业务回滚、8 次输入拒绝。四个场景 × 五类业务/状态产物的 **20 组比较全部一致**；四个场景的剩余 JDBC 事件也全部相同。数据库容器已清理，无清理错误。

| 场景 | 正常完成的 OrderStatus | 移除的展示查询 |
|---|---:|---:|
| baseline | 2 | 2 |
| holdout | 1 | 1 |
| transaction_edges | 3 | 3 |
| delivery_edges | 1 | 1 |
| 合计 | 7 | 7 |

正常与故障探针另计，不计入 124 条业务回放命令。组合版两个目标方法均不存在，四项 SQL 注册表与原版相同，方法删除顺序的源码相容检查通过。

已观察到的工作量变化是每次正常 OrderStatus 的业务读取 **5 → 4**；这里统计实际 SQL 执行次数，不代表耗时下降 20%。组合版未做延迟或吞吐计时，不能直接继承早期另一版本的 18%～22% 耗时结果。

组合版 `OrderStatus.class` 为 **4,990 字节**，姓名单删版为 6,688 字节，增量减少 1,698 字节。若与排除终端后的 7,540 字节基准相比，两个方法合计减少 2,550 字节。这些均为单个类的未压缩大小，不代表整个应用、堆内存或运行耗时的降幅。

## 故障反例与产物使用边界

对展示查询注入 SQLSTATE `58000` 后，原版报错，组合版因不再执行该查询而正常返回。该反例已保留，不能把“正常执行一致”表述为任意故障下能力完全一致。姓名查询在原版可调用，在组合版中不存在；原终端入口在组合版中明确拒绝。

组合版需要一起使用[新 JAR](../evidence/module-combined-pruning/20261105-454cdefc9245/combined/reference.jar)和[配套适配器](../evidence/module-combined-pruning/20261105-454cdefc9245/combined/adapter-classes/com/oltpbenchmark/api/TpccApp.class)。只替换 JAR、沿用原适配器会留下对已删除展示方法的调用。完整运行 classpath、共享依赖及命令保存在运行记录中；默认应用和历史归档未替换。
