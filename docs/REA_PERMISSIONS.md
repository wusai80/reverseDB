# 标签权限取证与待选方案

2026-11-03。当前任务仍是能力复现，数据库优化后置。

## 实测结果

在锁定的原版 Paperless 中，以独立 PostgreSQL 测试库和合成数据验证两个平面标签。
使用普通 owner、共享用户、无关用户、缺少模型权限的用户及匿名请求。
共享和撤销均由普通 owner 通过真实 HTTP 完成；没有安装 B1 补丁或 SQL trace。

第一轮 90 次请求，补齐同身份写后详情/列表读取后第二轮 106 次请求，集成测试均通过。
每轮检查四个阶段、五种身份的 20 组读取结果，并验证写入、拒绝后的状态和跨用户读回。

| 共享用户所处阶段 | 标签列表 | 详情 | 改名 | `user_can_change` |
|---|---|---|---|---|
| 私有、未授权 | 空 | 404 | 404 | 不可见 |
| 仅查看共享 | 两个标签 | 200 | 403 | false |
| 查看及修改共享 | 两个标签 | 200 | 200 | true |
| 撤销共享 | 空 | 404 | 404 | 不可见 |

获得修改权限的共享用户仍不能再次分享或删除，均返回 403；改名后的同一对象可被 owner 读到。
缺少模型级 `view_tag` 的用户即使获得对象级查看授权，仍返回 403。匿名请求返回 401。
无关用户始终看不到两个标签。拒绝的改名和删除不改变目标对象。

这些结论限定于本轮直接用户授权矩阵；未覆盖用户组、无所有者对象、管理员、所有权转移或并发。

## REA 生成路线遇到的难点

1. **身份与状态不能混为一谈。** 同一阶段，脱敏后完全相同的详情请求，owner 得到 200、其他用户得到 404；仅查看共享时双方都得到 200，但 `user_can_change` 不同。来源身份记录在独立实验时间线中，没有保留凭据。此前实际发现的五个 CRUD 工具只接收路径、查询和请求体，没有调用者身份参数；请求体的 `owner` 是对象字段，不能充当身份认证。
2. **按身份拆分会丢失其他人的写入因果。** owner 抓包看不到共享用户的改名调用；共享用户抓包看不到 owner 的授权和撤销调用。这样的独立状态服务无法据此自动保证所有人看到同一个对象和最新授权。

实际分身份生成两轮 bundle，没有合并身份输入。补采后 owner 仍只提供两个读取工具，PATCH 被标记 `unexplained-change`；共享用户也只提供两个读取工具，PATCH 为 `unconfirmed`，DELETE 为 `no-call`。删除本来就应被拒绝，不为提高覆盖率添加越权成功记录。

本轮补采消除了显式的即时读回缺口，但没有证明每个 withheld 原因的唯一根因；外部身份写入和授权变化仍存在。因此结论是**当前生成结果尚未复现多人权限闭环**，不是断言 REA 的所有功能都无法分析权限。诊断 bundle 仅保存在证据目录，未替换既有通过验收的 CRUD 原型，也未启动为多人服务。

## 待讨论的实现路线

推荐：保留 REA 的接口发现与状态变化证据，增加共享对象状态和显式权限层。

- 对象只有一份；调用者由可信会话绑定，不能让客户端随意填写用户 ID 冒充他人。
- 分开表示模型级权限、对象所有者和直接用户的 view/change 授权。
- 列表过滤、详情、修改及转授权使用一致的权限判断；撤销后下一次请求立即生效。
- 首先只实现已观测的普通用户与直接授权场景；未覆盖的管理员、用户组等不宣称支持。
- 用同一操作序列驱动原应用与副本，映射各自生成的对象 ID，对照可见对象、修改结果和拒绝后状态。

最小判别实验：新用户与新标签执行“私有 → 查看共享 → 修改共享 → 用户改名 → owner 读回 → 拒绝用户转授权/删除 → 撤销 → 用户访问被拒绝”。换一组用户和对象重复，防止把录制 ID 或结果写死。

代价是新增状态与权限实现、维护差分契约。每身份独立环境的工程量较小，但不自然支持共享状态及即时撤销；也可暂时限定单用户，先补其他业务能力。

**后续状态：用户提出以类似 TPC-C 的数据模拟多用户业务，已转入[订单场景实验](BUSINESS_SCENARIO.md)。** 多身份共享状态已成为实验方向；原应用的权限层尚未实施，手写场景模型不构成 Paperless 权限复现通过的证据。

手写权限层本身是普通工程实现。潜在研究问题是如何从保留身份与时间关系的观测中恢复权限规则、区分对象变化与视角变化，并以反例约束泛化；需要后续实验及相关工作比较，当前不宣称创新成立。
