# 模块依赖的分支上下文：从手工论证到自动提取

2026-11-04。已将[删除论证](MODULE_DELETION_ARGUMENT.md)中的接收对象推理落实到受限提取器。相同冻结源码中的展示调用，现在自动得到 `receiver_types = {OrderStatus}`，而不是混合四种事务类型。**本轮闭合的是这个调用点的对象来源关系，未闭合删除所需的全部效果义务。**

没有修改业务程序、运行新数据库实验或扩大性能矩阵。

## 规则与软件工程依据

采用以下充分条件关联两个 switch：

1. 对象初始化 switch 与包围调用点的 switch 使用同一个编译器变量符号，不按变量名称文本匹配。
2. 选择变量是 String 局部变量或参数，所分析源码中没有重新赋值。字段、复杂选择表达式不应用此规则。
3. 消费者分支是带常量字符串标签的箭头分支，没有贯穿和 guard；对象初始化也使用受支持的箭头分支。
4. 接收对象可追溯到未被重新赋值的局部初始化，沿用此前对直接 new、局部别名和 switch 表达式的限制。
5. 不把外层分支事实直接传入 lambda、嵌套类或嵌套方法等执行边界。

在这些条件下，到达消费者分支意味着选择变量属于该分支的标签集合；同一未改写变量在初始化 switch 中选择相应分配。多个标签取对应对象类型的并集；某个标签未显式出现于初始化 switch 时，可以选取其 default 分配。消费者的 default 分支暂不反推取值集合。

这是源码结构支持的参数化关系，不依赖某个客户、订单或测试事务值。规则不包含 OrderStatus、Payment 等业务名字。超出支持范围时保留原有类型集合或 unknown，不能猜测最可能的分支。

实现仍是受限规则，不是一般控制流、SSA 或路径证明器。为保持保守，即使一次赋值发生在调用之后，也会阻止用该变量收窄；这会损失精度，但本轮不扩展顺序敏感分析。

## 当前实例的变化

对同一冻结适配器、同一 `getOrderLines` 调用点，与上一版归档对照：

| 项目 | 前一版 | 本轮 |
|---|---|---|
| 不考虑分支时的对象集合 | 四种事务对象 | 同样四种，单独保留作为比较 |
| 当前调用点的对象集合 | 四种事务对象 | OrderStatus |
| 因类型不匹配而可能缺少方法的对象 | Payment、Delivery、StockLevel | 无 |
| 方法候选 | OrderStatus.getOrderLines | 同一个方法 |
| 调用可能失败 | true | 仍为 true |
| 效果摘要完整 | false | 仍为 false |
| 自动批准模块删除 | 否，unknown | 仍为 unknown |

提取记录保存三处来源：初始化 switch（冻结适配器第 55 行）、选中的对象分配分支（第 56 行）、消费者分支（第 78 行），以及选择变量符号和标签。这让“为什么选择这个接收对象”可以回到源码审查。

找到唯一目标不表示调用必然成功。反射桥的访问与参数条件、被调用方法的异常、JDBC 及外部库效果都没有被这条规则消除。反射桥的语义摘要仍由人工审阅并绑定源码摘要，本轮未改变这个证据等级。

## 实例与反例共同验证

保留此前全部 26 项检查，新增加真实调用点的前后对照和 9 个小型结构用例，共 **37 项检查通过**。这些新增用例是分析器的语法/符号实例，不是新增业务工作负载。

| 用例 | 预期与实际结果 | 检验的依据 |
|---|---|---|
| 标签 east 对应 RenderBox | 两类型收窄到 RenderBox | 不依赖 TPC-C 方法或标签名称 |
| 标签 west 对应初始化 default | 收窄到 OtherBox | 不总是选择第一个分配分支 |
| 选择变量被重新赋值 | 保留两类型 | 同一变量名不代表同一历史值 |
| 两个 switch 使用不同变量 | 保留两类型 | 相同标签不构成变量关联 |
| 传统冒号分支发生贯穿 | 保留两类型 | 到达语句不代表只匹配紧邻标签 |
| 接收对象被重新赋值 | unknown | 不能沿用旧初始化关系 |
| 调用延迟到 lambda 执行 | 不沿用外层分支收窄 | 本轮没有建模延迟执行上下文 |
| 消费分支有 east、west 两个标签 | 保留两类并集 | 不能随意选一个标签 |
| 调用位于消费者 default | 不收窄 | 本轮未计算补集条件 |

这里的负向用例检查规则是否保守，不是声称每一种不支持情况必然不安全。语法分析通过也不是对所有 Java 程序的正确性证明。

## 本轮结论与停止点

软件工程的源码论证已经在同一案例上转成可执行提取规则，并用独立结构实例检查了适用边界。原本的“混合事务对象”疑问在该调用点不再依赖手工判读。

剩余主问题收敛到：**删除该展示模块究竟需要哪些最小效果条件，哪些能从程序中确认，哪些必须由应用/数据库契约给定？** 当前仍未自动生成完整需求图，也未证明外部调用无相关效果，不能据本轮结果直接扩大删除范围。

分支规则到此冻结，不继续增加语法支持。下一步若继续，应围绕同一个模块的效果契约开展分析，而非扩展更多事务或缓存优化。
