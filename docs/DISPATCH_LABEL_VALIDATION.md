# 配置选路标注的独立核验

2026-11-06。结论：当前标注在固定验证范围内合理，但有明显的保守弃权。未发现“有限目标集合”遗漏测试中实际到达的目标；不能据此声称所有输入的准确率或完整程序的安全性。

本轮没有改动标注算法或业务实现。新增验证执行了 161 次 Java 控制流探针，并在临时 PostgreSQL 中采集两个函数目录快照；45 项检查通过。没有业务事务、业务数据集或性能测试，临时容器已清理。

## 独立依据

此前测试主要检查 AST 提取结果是否符合预设结构。本轮增加两个不同来源的核验：

1. 编译并实际执行原 FusedNewOrder，以及 22 个 Java 守卫方法，使用连接代理在 prepareStatement 边界记录真实 SQL 后停止。这样由 JVM 决定控制流，不复用静态分析器来预测执行路径。
2. 在无业务数据的隔离 PostgreSQL 中安装实际归档的函数定义，直接查询 pg_proc，核对被标为“函数体缺失”的目标。没有执行这些函数的业务 SQL；定义存在不等于函数执行成功或语义等价。

Java 探针验证调用目标，不代替此前完整端到端业务验证。代理在 SQL 构造完成、即将准备语句时停止，不模拟后续数据库结果。

## 标注与实际观察

| 标注维度 | 核验结果 | 可得出的结论 |
| --- | --- | --- |
| 实际 NewOrder 的有限目标集合 | 7 个配置包含默认值、4 个白名单值和2个非法值；4个目标均实际到达，非法值均在 JDBC 前被拒绝 | 该实际案例的四个候选都应保留，默认值不能抹去其他模式 |
| 5 个控制例的有限集合标注 | 每个例子执行7种固定输入组合，观测目标均在静态集合内，集合中的每一项均被执行覆盖 | 固定矩阵中未发现错误排除目标；不把测试覆盖当作全域证明 |
| 17 个未知控制例 | 每个例子至少一次到达 JDBC，有些到达白名单外目标，有些只出现集合内目标 | unknown 既不是不可达，也不是已知错误，必须继续保留 |
| 当前部署目录下的缺失函数 | PostgreSQL 中确实缺少 pruned、early_write、full_fault 三个 NewOrder 定义 | “目标集合已知”与“函数体可用”必须分开标注 |
| 加载全部归档定义后的目录 | 四个 NewOrder 定义均存在，相应缺失标记消失 | 标注随实际函数目录变化，不应把缺失函数永久视为无用模块 |
| 自动删除资格 | 两种目录下均为 false | 这些局部标注还不足以授权删除 |

“观察遗漏为 0”只描述本次固定矩阵。对“未知”的样本不计算虚构的误报率、召回率或概率置信度。

## 两个新反例

在既有20个结构控制例之外，加入两个新的绕过情景，每个同样执行7个固定输入：

- 拒绝式检查位于 try 中，SQL 调用位于 finally。非法配置即使引发异常，也仍会走到 SQL。
- 非法分支抛出的异常在该分支内部被捕获，然后继续调用 SQL。

两者均保持 unknown，实际执行均能到达 `demo_gamma` 等白名单外目标。没有错误继承其他代码块中的守卫约束。

初次探针执行 [20261106-64ee3be485c7](../evidence/dispatch-label-validation/20261106-64ee3be485c7/run.json)因反射枚举包含编译器生成的 lambda 辅助方法而失败，尚未创建数据库容器。修正探针为仅枚举非 synthetic、且参数签名匹配的测试方法后，在同一固定范围完成验证；没有调整标注算法以适应测试。

## 当前标注的不足

保守弃权确实存在。例如 return 形式的拒绝，以及实际会执行的 lambda 校验，当前规则均不识别；本次执行观察到的目标仍只有 alpha/beta。这不是它们错误或无用的证据，而是分析器尚未建立相应控制关系。也不能仅凭这几次观察把 unknown 升级成已证明的有限集合。

因此后续应保持四个维度分离：

```text
调用目标集合：已收窄 / 未知
函数定义：可用 / 缺失或有歧义
行为与效果：已检查的局部事实 / 仍有未知
删除资格：独立判断，当前未授权
```

本次核验的结果无需修改当前标注。下一步如果扩展规则，应优先处理实际阻碍融合的未知项，而不是仅为了提高标注覆盖率识别更多写法。
