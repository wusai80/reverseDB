# 多用户订单业务实验

**最新路线纠正：** 此文的内存模拟器保留为自定义场景草案。用户要求不受工具链限制后，已确认 TPC-C 无需 GraphQL/REST；后续优先复用数据库事务实现和多终端驱动，不先启动 Saleor 或开发协议适配。[当前执行计划与依据](TPCC_ROUTE.md)。下文有关 Saleor/GraphQL 的候选步骤属于历史讨论，已不作为前置要求。

## 与 TPC-C 的关系

TPC-C 提供订单录入、付款、订单查询、交付及库存查询五类事务，组织背景为仓库、地区和客户。它同时规定了数据规模、事务行为和测量方法，详见 [TPC 官方概览](https://tpc.org/tpcc/detail5.asp)及 [规范 Revision 5.11](https://www.tpc.org/TPC_Documents_Current_Versions/pdf/tpc-c_v5.11.0.pdf)。

本实验借鉴业务结构和操作类型，使用自行生成的微型合成数据，**不是标准 TPC-C 实现、数据集或性能结果**。付款绑定单笔订单、付款后才交付、库存不足拒绝、按仓库划分角色、订单查看授权与撤销，均是本实验自行定义的规则，不能归为 TPC-C 或原应用的规则。未实现完整九表、标准规模、事务混合比例、NURand 分布、远程供货、标准库存更新公式或 tpmC 测量。

## 已运行的场景

默认种子 42：2 个仓库、每仓库 2 个地区、每地区 10 个客户、100 种商品、200 条仓库库存。初始 11 个身份：每仓库有经理、销售、财务、履约人员和一名客户代表，另有外部审计员。并发阶段额外加入第二名同仓库销售，共 12 个模拟身份，其中 9 个实际参与这条操作序列。

| 业务阶段 | 操作者 | 检查内容 |
|---|---|---|
| 建单 | 仓库 1 销售 | 扣减对应库存，计算以分为单位的金额 |
| 查询 | 客户本人、另一仓库客户/经理 | 本人可见，另一仓库不可见 |
| 临时查看授权 | 仓库经理、外部审计员 | 授权后可读，审计员仍不能付款或转授权 |
| 收款 | 财务 | 同一幂等键重试不重复记账 |
| 履约 | 仓库人员 | 未付款不能交付，付款后客户可查到已交付，重复交付拒绝 |
| 撤销授权 | 经理、审计员 | 撤销后的下一次读取被拒绝 |
| 无效订单 | 销售 | 不存在商品或库存不足时，订单和库存都不发生部分更新 |
| 库存争用 | 两名同仓库销售 | 通过线程屏障同时开始，最后一件商品只有一人成功 |

主运行完成 23 次模拟操作、22 项检查。种子 43 也通过同一流程；相同种子数据一致，不同种子改变价格。事件记录操作者、操作序号、参数、结果及状态是否变化。并发赢家不固定，验收只要求一成一败及库存不为负。

## 验证边界与下一步

运行器是**我们手写的内存业务模型与可信测试驱动器**：没有数据库、HTTP 服务或生产认证。角色由驱动器选定；没有把任意用户提交的 actor ID 当作已认证身份。共享状态由一把进程内锁保护；本轮并发检查不证明数据库事务隔离、死锁处理或吞吐能力。

输出明确标注 `application_observed=false`、`rea_reconstruction_validated=false`。模型自测只能验证夹具内部的一致性，不能作为真实应用行为或 REA 恢复成功的证据。负例和权限规则目前都是人工设计，尚无创新结论。

下一步接入选定真实应用：数据装载 → 真实会话绑定 → 操作序列适配 → HTTP/GraphQL 捕获 → REA 分析 → 副本差分。跨系统对象 ID 要以返回值建立映射，不能写死或假设两边相同。当前仓库已有 Saleor 源码可作为候选，但尚未启动 Saleor，也未选定其接口适配和权限映射；例如锁定源码中履约使用 `MANAGE_ORDERS` 权限，不能假定它天然具有本实验的细分角色或仓库隔离。

后续已完成 [REA GraphQL 协议前置实验](REA_GRAPHQL.md)：当前环境生成路线将同地址的不同 POST 操作合并，合成夹具生成的实际工具目录为空。已提出协议适配方案，等待路线选择；此阶段尚未产生真实 Saleor 请求，不能把协议测试当作订单应用复现。

权限取证此前提出的“多身份共享状态”现已成为实验方向；真实应用权限层的实现仍需以目标行为为依据。当前夹具不替换 Paperless 的 REA CRUD bundle，不声称已解决其多用户权限缺口。

## 运行与资源

```sh
python3 prototype/business_scenario/simulate.py --seed 42 --output work/business-scenario/new-run
python3 -m unittest discover -s tests -p 'test_business_scenario.py' -v
```

仅需 Python 标准库，输出目录必须不存在。生成器设有小型数据上限，CLI 当前只开放种子，不开放大规模压力参数。尚无自动资源监控或远程调度实现。

本轮只读检查：宿主内存 32 GiB、逻辑 CPU 12；Docker 内存约 7.7 GiB，当时无运行中的容器；磁盘可用约 44 GiB。未发现需要立即迁移的负载迹象，当前夹具无需 GPU。检查值是当时快照，不是运行期间峰值监测。

远程服务器可用于较大数据库、并发负载，以及以后需要的模型推理。迁移前需要已有 SSH 别名、可用目录、CPU/内存/磁盘和容器架构；不需要在聊天中提供密码或私钥。当前未收到连接信息，未连接或上传任何数据。该标准库模拟器可原样运行；实际应用容器需要重新核对架构，不能直接假定本机 arm64 镜像适配远端。
