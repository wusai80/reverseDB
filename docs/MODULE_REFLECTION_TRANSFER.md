# 已有反射桥的实参—形参映射

2026-11-05。已为现有 `TpccApp.invoke` 桥补上来源绑定的参数映射：**真实适配器的 22 处反射调用均确认了唯一目标、参数位置及本轮支持的类型对应关系。** 其中三个目标的方法体在当前两份源码范围内，新增 54 个目标内部调用上下文；其余 19 个目标仍缺少本轮已分析的方法体。

这证明了限定桥上的映射关系，不证明反射调用必定成功，也不证明全部路径可执行。本轮保留原桥调用及错误义务，没有删除模块、全局调用边、数据或业务能力。

## 桥接条件来自哪里

已有适配器的桥按接收对象实际类的 `getDeclaredMethods()`，使用方法名和参数个数选方法：零个匹配报错，多个匹配也报错；随后设置访问权限，使用同一参数数组调用目标，并转发目标异常。

本轮沿用此前人工审阅、绑定方法文本 SHA-256 的语义摘要。提取器执行前核对摘要对应的桥源码；把 `getDeclaredMethods()` 改成 `getMethods()` 的变体已被拒绝。没有把这个规则推广成任意 Java 反射语义。

目标唯一性不能靠参数类型猜测。因为这个桥**在类型转换前就拒绝同名、同参数个数的重载**，本轮严格保留这一行为。

## 映射与拒绝条件

映射要求接收对象类型唯一、目标唯一、没有缺失或歧义候选；桥的两个前置参数是 target/name，因此目标第 i 个形参对应桥的第 i+2 个实参。输出保存目标签名、形参名/类型、实参类型/位置、源码位置、参数总数及桥摘要哈希。

类型检查支持原始类型精确对应、精确包装类型的情况，以及可证明的引用赋值兼容。包装值仍可能为 null，访问控制、目标异常及其他调用失败均保留；不会由类型兼容推导正常执行。数值拓宽虽然在某些反射调用中合法，本轮仍不支持并返回 unknown。

以下情况保持未知：

- 动态方法名、接收对象可能被改写、多个接收类型、缺失目标或同名同参数个数重载。
- 打包的 Object[] 参数、未强转的单个 null 可变参数调用，以及目标本身声明可变参数。
- 静态类型无法证明兼容、源参数证据不完整、索引/类型证书不一致、桥哈希失效。
- 目标通过继承获得而非当前类直接声明——当前桥只查 `getDeclaredMethods()`，不能擅自补上继承方法。

部分拒绝表示本轮分析不支持，并不等于程序一定出错。

## 实际参数例子

适配器的展示查询调用：

```java
invoke(p, "getOrderLines", c, 1, d, order.o_id, cust);
```

| 目标参数位置（从 0 起） | 桥实参位置 | 实参表达式 | 目标形参 | 已核对类型 |
|---:|---:|---|---|---|
| 0 | 2 | `c` | `conn` | Connection |
| 1 | 3 | `1` | `w_id` | int |
| 2 | 4 | `d` | `d_id` | int |
| 3 | 5 | `order.o_id` | `o_id` | int |
| 4 | 6 | `cust` | `c` | Customer |

位置和类型映射已成立，不表示求解器理解了所有值域。当前条件替换仍只支持稳定 Boolean/String；整数、连接和 Customer 对象值保持未建模。没有把订单 ID、客户或金额限制为测试样本中的值。

## 如何接入已有分析

在原桥调用之外，增加“成功进入已绑定目标时”的条件视图。原桥调用、反射操作及失败路径继续保留。目标方法体不可用时，参数表可以记录下来，但进一步分析明确停在外部方法体边界。

有源码的目标沿用上一阶段的一次方法边界组合：调用位置条件加上实参替换后的内部条件。递归检测包含新增的反射目标边；递归或延迟上下文仍为 unknown。一个上下文矛盾不影响同一目标的其他调用位置。

默认直接调用分析保持原行为，反射传递由显式选项启用。原有 376 个调用位置对的记录和判定全部保留。
