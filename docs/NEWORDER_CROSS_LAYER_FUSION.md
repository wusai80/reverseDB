# NewOrder 反编译后的跨层融合

2026-11-05。固定实验完成，容器与磁盘卷已清理。

后续已完成[融合区域与计划门控](FUSION_REGION_ANALYSIS.md)：增加静态依赖分析和正常生成入口检查，后端产物与本文归档一致，未新增数据库运行或性能数字。下文保留首轮融合实验的范围与结论。

## 本轮结果

从冻结的反编译 NewOrder 和应用适配器恢复事务步骤，生成 PostgreSQL 内的执行函数。NewOrder 路径改为一次外层 JDBC 调用，原 Java NewOrder 类在融合版回放中不再加载。原版、保留检查的融合版、融合后删除重复仓库检查的版本，各执行既有 62 条固定命令；响应、逐步业务观察、完整九表初末状态和不变量均与冻结基准一致。

三个固定订单的事务主体中位耗时下降约 88%～91%。融合后再删仓库检查的增量结果不稳定，不能声称有额外加速。完整数据没有裁剪，WAL、行锁、SERIALIZABLE 与同步提交保留。

这是一条**绑定特定源码的受限转换链**，不是通用编译器。数据库仍是原 PostgreSQL；尚未反编译其内核，也没有移除 SQL 执行器或全部 JDBC。

## 新的执行布局与生成依据

```mermaid
flowchart LR
  S[冻结的反编译 NewOrder + 适配器] --> E[带类型的调用与 SQL 提取]
  E --> I[事务中间表示 + 源位置]
  I --> G[人工定义的受限后端规则]
  G --> P[数据库内 NewOrder 函数]
  A[原应用验证与事务边界] --> J[一次 JDBC 调用]
  J --> P
  P --> D[原数据库读写、锁与 WAL]
  P --> R[完整订单与明细结果]
```

原路径在应用进程中执行适配器、反射桥、过程初始化、各 Java 辅助方法，以及逐步 JDBC 参数绑定和结果读取。新路径将辅助方法的 SQL、必要标量计算、暂存数组和两个写入阶段放进数据库函数；应用只传入整个命令并接收完整结果。其他四类事务继续使用原路径，原 JAR 仍在依赖中，本轮没有物理裁小整个 JAR。

- [实验驱动](../scripts/test_neworder_fusion.py)：资产校验、生成、三臂回放、模式准入及清理。
- [计时和反例夹具](../prototype/module_pruning/FusionProbe.java)：同一 JVM 中隔离加载各版本。

中间表示包含十项原始 SQL、JDBC 参数绑定及位置、九个直接辅助调用的顺序、两个批量写入阶段、十个地区分支、库存计算常数、Java 浮点规则，以及适配器的三项结果相关查询。仓库、供应仓库和 all-local 的常量来自已有适配器，不从测试数据归纳。

后端的循环结构、异常映射、表示转换和合法改写规则仍由我们编写。源代码版本必须先通过归档哈希校验，提取后的受支持结构也必须匹配；本轮验证了未知源码及不兼容批次顺序会被拒绝。规则并未自动发现，更没有自动证明任意新程序可以转换。

PL/pgSQL 在数据库进程内运行，其 SQL 仍通过 PostgreSQL 的执行机制处理，包含可缓存的语句计划。因此本轮实现的是执行位置与调用边界改变，不能称为直接访问原生存储 API。[PostgreSQL 实现说明](https://www.postgresql.org/docs/18/plpgsql-implementation.html)。

## 能力与改写义务

以原程序 P、原应用合法输入域 I、满足模式契约 C 的数据库状态 D 为对象，目标义务是：对允许的串行执行，融合程序 F 保持业务观察与事务最终状态，即 `Obs(P, x, D) = Obs(F, x, D)`；失败路径还须保持原子回滚。这里的输入域和状态契约独立于有限测试数据。该等式是需要论证的目标，不是本轮有限回放已经证明的定理。

本次结构性约束如下：

| 义务 | 处理方式 |
| --- | --- |
| 原应用合法输入 | 保留 AppRuntime 验证，包括 5～15 行订单；不按样本商品 ID 特化 |
| 完整业务数据 | 不删行、不删列、不缩小商品或地区数据域；完整 SELECT * 输出保留 |
| 控制与数据依赖 | 先执行检查和订单头写入，读取并暂存所有明细，再写所有明细，最后写所有库存 |
| 表示一致 | 保留 float32 乘法再拓宽到 double 的金额路径；时间戳使用固定时钟及原 JDBC 时间转换实现 |
| 事务效果 | 外层 SERIALIZABLE、提交/回滚保留；库存与地区 FOR UPDATE 保留；持久化设置开启 |
| 额外仓库检查删除 | 仅 pruned 臂使用先行客户检查及有效、强制、不可延迟的客户→地区→仓库外键链 |
| 未知情况 | 不接受其他源码版本；并发、任意异常时序、触发器/RLS 等不纳入当前转换结论 |

实验恢复锁定的完整数据库快照，并检查普通表、无用户触发器/规则/RLS、外键与其触发器启用、时间戳列结构、正常复制角色和持久化设置。SQL 批次在后端降为按原顺序逐行执行，原 JDBC 批次可能被驱动合并；因此不声称 SQL 事件序列、任意故障点或触发器行为相同。

检查仅由实验驱动执行。生成函数单独安装并不自动获得这些准入保证，也没有生产环境自动回退。过程注册表、任意反射入口、调试日志和 SQL 轨迹身份不是保留的业务观察。

## 关键难点与反例

**读取和写入阶段不能随意交错。** 原 NewOrder 先读完每一行的库存，再批量更新。重复商品会多次读到更新前的库存；数量列最终采用最后一次暂存值，而计数与累计数量逐次增加。若融合时改为“读一行就更新一行”，语义就变了。

冻结的 `new-05` 重复商品用例区分出了故意错误的 early_write 版本：原版库存数量为 76，错误版本为 75；两者累计数量均为 3、订单计数均为 2。这说明只比订单返回值或累计计数不足以检查改写，必须追踪读取依赖和完整写入效果。该测试只作见证，不参与选择可删除数据。

**晚期失败必须撤销所有写入。** 原版在完整写入后的订单结果查询处注入 SQLSTATE 58000；融合测试版在对应结果投影前抛出同状态异常。两者经外层回滚后九表完整哈希都与初始状态一致。数据库函数错误自身还具有语句回滚行为，因此本测试只声称外层事务结束后的原子性一致，不声称中间故障机制相同。

**表示转换也属于程序语义。** 直接采用数据库更高精度金额运算会跳过原程序 float32 舍入。生成器明确保留该规则，结果时间戳也经相同版本的 PostgreSQL JDBC 转换。此处使用人工核验规则，尚无通用跨语言类型求解器。

## 固定验证与性能

四个既有场景为 baseline、holdout、transaction_edges、delivery_edges；每臂共 62 条命令，50 提交、4 中止、8 输入拒绝。三臂合计 186 条命令。每个场景都检查响应、逐步业务观察、九表初末状态和五项不变量；非 NewOrder 的 JDBC 事件与原版相同。两种融合臂均未加载原 Java NewOrder 类。

每臂共有 14 次已接受的 NewOrder 执行，原版累计 308 次 JDBC execute，融合版与融合删减版各 14 次。计数是 JDBC 方法调用数，不等同于网络包数或服务端 SQL 数。

计时为同 JVM、同数据库、三个符合应用输入约束的固定命令，每臂每命令预热三次，随后十个打乱臂顺序的测量块，种子 20261105，共 90 个计时调用。每次执行后回滚；计时包含事务主体及完整结果组装，不含提交、回滚、验证和环境准备。

| 命令 | 特征 | 原版中位 ms | 融合 ms | 融合＋仓库删减 ms | 融合相对原版下降 |
| --- | --- | ---: | ---: | ---: | ---: |
| new-01 | 5 行 | 8.179 | 1.001 | 0.956 | 87.8% |
| new-04 | 15 行 | 14.378 | 1.316 | 1.326 | 90.8% |
| new-05 | 5 行，含重复商品 | 7.149 | 0.836 | 0.852 | 88.3% |

三个命令的 JDBC execute 分别由 21、41、21 次变为各 1 次。融合之后额外删除仓库检查的中位变化分别为降低 4.6%、增加 0.7%、增加 1.9%，没有稳定的增量收益。

这组计时说明当前本地 Docker、驱动、代理观测及固定串行负载下，改变执行位置的潜在收益明显大于再去掉一个小查询。它没有单独分解协议、驱动、初始化、结果组装和执行计划缓存的贡献；不能把差值全归为网络延迟，不能推导并发吞吐或正式提交的整体加速，也不能与历史版本的耗时相加。
