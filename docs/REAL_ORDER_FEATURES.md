# 真实融合SQL的顺序关系特征

2026-11-06。将前轮小模型中的关系特征落实到已冻结的 NewOrder 融合SQL，比较正常版本、提前写库存版本和一个独立结果查询换序候选。**相同Java参数绑定下，SQL内部的顺序变化可以产生不同的关系特征。** 本轮没有迁移小模型系数、拟合概率或新增数据库执行。

## 从代码恢复什么

读取历史归档的 `full.sql` 与 `early_write.sql`，核验哈希。从固定生成格式中的13个SQL位置恢复读表、写表、SELECT INTO局部定义、显式局部引用、FOR循环归属及语句次序。语句按规范化内容匹配，三个版本的SQL语句集合完全相同。

这是限定于现有单行SQL、平层FOR循环格式的扫描器，不是通用PL/pgSQL解析器。它输出结构事实和数值特征，不使用“正常／错误”命名来赋分，也不把冲突当作错误判断。IF及错误控制、非SQL标量赋值、约束／触发器、隐藏调用和锁调度没有形成完整摘要；“没有已提取冲突”不能当成全程序安全证明。

固定按5和15次迭代展开静态操作位置，分别对应应用允许的订单行数边界。展开不填商品ID、库存值或其他业务数据，也不执行SQL；不能将其计作业务用例或所有输入的验证。同表访问按可能别名保留，重复商品始终允许，不以当前数据是否重复来裁剪依赖。

特征包含反转操作对数、其中潜在同表读写冲突数、跨迭代冲突数、已提取局部值依赖、写入之间的顺序变化，以及操作对归一化比例。比例的分母受展开长度影响，不能直接解释为故障概率。

## 三组对照

| 候选 | 5次展开的顺序反转 | 其中同表读写冲突 | 其中跨迭代冲突 |
| --- | ---: | ---: | ---: |
| 正常版本原顺序 | 0 | 0 | 0 |
| 交换两个最终结果查询 | 1 | 0 | 0 |
| 提前写库存 | 45 | 10 | 10 |

15次展开时，独立查询仍只有1对反转、0对冲突；提前写入则有435对反转、105对跨迭代库存读写冲突。数量是静态操作对，不是实际碰撞、失败次数或独立训练样本。

真实差异可以表述为：原版先完成 `R(stock,i)`、`R(stock,j)` 再写；提前写入让 `W(stock,i)` 越过后续 `R(stock,j)`。当 `i<j` 且可能是同一商品时，后续读取可能看到已修改数量。已有实际五行探针保留最终库存76／75的反例，本轮只核验其归档。

此外，提前写入还反转了25／225对库存写入与订单明细写入。它们没有同表交集，但约束等机制仍可能联系不同表；本轮保留这个特征，不把同表冲突之外的变化宣布为无影响。

## 合法换序对照的依据与限制

从正常SQL构造一个候选，只交换末尾相邻的两条结果查询：分别读取订单头和订单行，定义 `v_order_json`、`v_lines_json`。其余语句、循环、所有业务数据及最终JSON构造保持一致。

在冻结普通表模式、串行相同可见状态、两条查询正常完成、不要求SQL轨迹／错误时序相同的条件下：

- 两条查询均为只读且不带FOR UPDATE；
- 定义的局部变量不同，彼此不消费对方的结果；
- 中间没有数据写入；最终返回使用同名变量，随后没有观察两条查询留下的FOUND等诊断状态。

因此两次赋值可以交换，完整返回与业务状态保持一致。这是已核验具体源码上的条件化论证，不是扫描器仅凭“0冲突”得出的通用规则。候选SQL已保存但未部署，**没有新数据库实测标签**；训练准入仍为false。

正常版本的旧固定回放通过与提前写入的旧反例分别保留，不将旧回放通过升级为全能力等价，也不把新换序候选的源码论证伪装成执行结果。

## 验证与下一缺口

七类检查通过：不变顺序为0反转；三个版本SQL集合相同；结果查询换序只有一对独立反转；两种展开长度均恢复后续库存读写关系；两个结果局部变量独立；表名／函数名变化不制造特征差异；历史源码与执行证据哈希一致。

本轮补上的是**真实代码能否提供关系特征**，不是模型泛化。仍只有一个生成程序来源，尚缺同一验证边界下多个真实候选的执行标签；不能直接套用人工原语模型的概率。下一次有价值的验证是把独立查询换序与错误写序放入同一固定端到端协议，保留完整状态，再考虑是否具备学习对照，而非继续堆解析规则。
