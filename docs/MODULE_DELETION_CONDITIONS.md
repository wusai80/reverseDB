# 模块删除条件：需求闭包、效果与构建边界

2026-11-04。接续[单模块删减验证](MODULE_PRUNING_PILOT.md)，本轮把删除条件写成一个可执行的有限图模型，并绑定到已有反编译产物。没有新增业务模块、数据库实验或性能调优。

后续已完成[受限依赖事实提取](MODULE_DEPENDENCY_EXTRACTION.md)；自动分析仍未闭合摘要，不改变本文人工模型的证据等级。

核心问题是：**在保留哪些能力的约定下，哪些模块可以整体移除？** 模块调用次数和覆盖率不回答这个问题；一个每次都执行的模块也可能不服务于保留能力。

## 能力先于依赖图

定义契约 C = (E, O, A)：

- E：保留的入口及输入范围。本例是应用适配器的 OrderStatus 分支，不是任意反射入口或原 BenchBase 终端入口。
- O：必需观察，包括完整响应、业务错误和数据库状态；是否包含终端展示、查询审计、注册表观察，需要明确声明。
- A：环境与完成性条件，如固定快照、串行调度、被删模块正常终止、无读查询外部副作用。

目标是对所有满足 C 的输入和状态保持观察等价。测试集合 W 用于找反例与测成本，不能替代 C，不能把 W 未出现的数据或分支直接排除。

**异常不只是一个可选观察。** 如果模块抛错会阻止后续 JSON 生成，那么即使用户不关心异常文字，也仍然有到最终响应的控制依赖。不能用“错误信息不需要”许可删除。本例的正常执行假设排除了这类执行；如果异常可能发生或情况未知，就需要保留或报告未知。业务缺失检查不属于被排除的查询故障，仍然保留。

## 从调用图到需求图

建立图 G=(V,D)，边方向统一为“消费者/观察 → 它依赖的提供者”。节点可以是输出、功能区域或共享资源。边区分数据、业务错误、异常控制、终止性、状态效果、查询观察、反射及共享调用。

调用图提供候选关系，需求图表达它为什么必须存在。若把所有调用无条件当成必需依赖，原程序调用的全部模块都会被保留，无法识别此次展示模块的删减空间。另一方面，单看返回值数据流又会漏掉异常、状态和其他消费者。

本例的主要关系如下，省略部分传递边：

```text
完整应用结果 ──→ 客户读取/存在检查 ──→ 共享 PreparedStatement 工厂
             ├─→ 最新订单选择 ──────→ 同一工厂
             ├─→ 订单头 JSON
             └─→ 有序明细 JSON

终端展示（若保留） ──→ 明细展示模块 ──→ 专属 SQL 定义
查询审计（若保留） ──→ 明细展示模块
完整应用结果 ──[模块可能失败或不终止]──→ 明细展示模块
数据库状态 ──[模块可能有可观察写效果]─→ 明细展示模块
注册表观察（若保留） ──→ 专属 SQL 定义
未解析反射调用（未知） ──?──→ 明细展示模块
```

最后几条是需要检查或声明的义务，不是说这段 SELECT 已被发现有写入或不终止。现有反编译方法、适配器及历史运行证据提供部分依据；其余环境条件仍是人工假设。

## 三态规则

每个入口和边条件取 true、false、unknown。只沿已知成立的条件求闭包 L；把未知也作为可能成立求闭包 U。对于待删节点集合 M：

| 条件 | 判定 | 行动 |
|---|---|---|
| M ∩ L ≠ ∅ | retain | 保留，并输出通向该模块的依赖路径 |
| M ∩ L = ∅，M ∩ U ≠ ∅ | unknown | 存在可能依赖，暂不删除 |
| M ∩ U = ∅，但来源、完整性或变换边界未闭合 | unknown | 补足缺失义务，不能以测试通过代替 |
| M ∩ U = ∅，且义务均在声明范围内成立 | conditionally_deletable | 仅作为条件化删除候选 |

L、U 是**给定图**的闭包，不是算法自动得到了真实程序的必要性上下界。若图遗漏真实依赖，闭包结果也可能不可靠。因此依赖摘要完整性是一项独立义务，源文件哈希和文本锚点不能证明它。

图内未知条件的保守处理允许多保留模块，不能允许错误删除。在满足图与效果摘要保守、来源有效、变换边界正确等假设时，真实需求包含在 U 内，删去 U 外的区域才有条件化依据。实际 Java/JDBC 语义与此抽象的对应仍是手工论证，不是形式验证器已经证明的结论。

实现是通用的有限图遍历，不把 OrderStatus 名称写入判定分支。[图与人工事实](../prototype/module_pruning/demand_graph.json)和[判定函数](../prototype/module_pruning/demand_model.py)分开保存。这里不引入成本求解：首先判断是否允许删除，再考虑是否值得删除。

## 为什么粒度要由边界约束决定

在同一份依赖图上比较三个粒度，无需继续增加事务或数据：

| 删除单位 | 结果 | 原因 |
|---|---|---|
| 整个 OrderStatus 类 | 必须保留 | 包含客户检查、最新订单选择等必要职责 |
| 展示方法 + 专属 SQL 定义 | 条件化可删候选 | 当前应用不消费展示结果，相关效果受明确条件约束 |
| 仅删除 SQL 字段 | 暂不能删除 | 原方法仍引用字段，调用与构建边界未闭合 |
| 展示模块连同共享帮助方法 | 必须保留共享部分 | 客户和订单模块仍使用同一帮助方法 |

因此“未被需求”与“删除后可构建”是两道不同条件。必须说明调用点如何移除、被排除入口如何阻断、反射/注册表怎样处理、共享资源由谁保留。此前特化产物把原 BenchBase run 替换为拒绝桩，只是这一个画像的有效边界处理，不能授权对任意模块采用相同做法。

一个待研究的粒度原则是：寻找**具有可描述职责、边界可闭合、且没有保留需求的区域**。本轮只比较了人工给出的粒度，没有提出或证明最优模块划分算法。

## 本轮检查与证据等级

[离线验证器](../prototype/module_pruning/check_demand_model.py)完成：

- 10 个来源锚点与相关归档文件摘要核验。绑定展示方法、专属查询、两个消费者、客户/订单错误和共享调用。锚点匹配不是程序分析。
- 17 个判定案例：展示模块的条件化候选；必要客户/订单模块、整类和共享帮助方法保留；增加展示、查询、反射或效果需求后保留；关键事实、图完整性或边界未知时不删除。
- 对 3 个未知条件枚举 8 种补全，验证确定闭包与可能闭包包住每个补全的图内需求。
- 对 7 个布尔条件的 128 种画像检查 448 次单条件扩展，本图中增加观察/可能效果不会缩小需求集合。这是本图的性质，不是任意程序的泛化证明。
- 删除异常控制边、删除查询观察边两个错误模型，都会错误允许删减；分别被已有的故障响应差异、5 次与 4 次查询记录所否定。这里只复核旧证据，没有再执行故障注入或数据库计时。

手工依赖摘要完整性和环境假设被明确标记为声明；编译和类加载证据只绑定此前那一个具体变换。没有把这些条件从 unknown 偷换成自动证明。

## 已收敛的研究难点

当前缺口不在闭包遍历本身，而在**从反编译程序建立可信的模块需求与效果摘要**。要同时解决：

1. 从实际应用入口追踪消费者，包含已知反射调用；未知目标产生可能依赖，不能因为没有日志就忽略。
2. 区分值、业务错误、异常/终止控制以及数据库效果；说明哪条边由源码支持，哪条依赖环境假设。
3. 沿这些依赖选择合适的区域边界，输出可核验的删除理由及尚未满足的义务。

候选研究产物是“模块删除说明”：来源绑定、能力契约、依赖路径、效果假设、边界修改和反例，而非一个只有 keep/delete 的标签。模块切片和闭包算法本身不构成新的学术贡献；能否从反编译与数据库交互中恢复足够可靠的上述信息，仍需后续研究验证。

本轮在这三个问题及一个可执行的条件模型处结束。没有新增业务变换，也不自动启动完整编译器、更多模块或工程调优。
