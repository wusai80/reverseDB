# 相同源码解析结果的复用

2026-11-04。本轮只复用源码文本的纯语法分析结果，实时核验规则保持不变。**104 项测试通过，300 个本机热态样本中，新版完整调用中位耗时比上一阶段版本下降 61.14%～61.27%，约从 60～63 ms 降为 23～24 ms。** SQL 总数仍为 27 条，完整结果、SQL 与参数均一致。本轮已完成并结束。

## 改动与有效期边界

源码 views.py 约 212 KB。此前每次创建候选和执行前来源核验都重新运行 AST 提取。初步本机源码分析将重复解析定位为开销线索；最终判断采用冻结 Docker 环境中的完整调用对照。

[接入层](../prototype/aggregate_reattach/callsite_binding.py)新增单项 LRU，仅以完整源码文本为键，保存不可变 JSON 字符串。读取时解码出新的结构，调用方修改候选不会修改缓存。不同源码文本使用不同键，最多保留一项；解析异常不缓存。缓存不跨进程持久化，当前提取器实现作为本进程固定代码使用。

每次仍重新读取 views.py 并验证固定 SHA-256，再使用解析结果。模型与关系字段解析、人工审计策略匹配、manager、helper 运行时代码、schema、身份、查询、声明、事务和单次 token 核验继续执行。缓存中没有数据库事实、准入结论、用户查询结果或可执行 SQL。因此没有新增 schema 有效期或跨调用复用准入证明的假设。

冷缓存的第一次完整调用解析一次，执行前可复用同一文本结果；后续热调用解析零次。来源文件发生变化仍先在来源检查处拒绝。这是纯语法结果与实时核验的职责划分，不是从有限行为推导系统能力，也不作为方法新颖性结论。

## 同轮完整调用测量

旧版来自上一阶段的归档接入层，SHA-256 为 `b583f9ecc44c155e99ec61d7ea20692f5c22c82fa416da3a2918307f6a3b74b2`。两版共享未修改的底层绑定器与 SQL 生成器。

复用 Tag、CustomField 的 mixed/dense 四个数据场景。每场景比较旧版、新版及原 helper；每方法预热 2 次，5 个时间区块各 5 轮，以种子 20261104 固定打乱顺序，每方法每场景 25 个样本，共 300 个。每次新建 QuerySet，计时包括候选创建、执行前核验、数据库调用与完整结果返回；结果校验在计时后。离线提取输入预先准备，两版的来源核验均在计时边界内。

计时期间关闭 query logging 和 trace；解析次数、SQL trace 与 cProfile 均单独采集。这里测量的是预热后的缓存效果，冷路径只验正确性和解析次数，不宣称冷启动时延。cProfile 累计时间包含嵌套调用且受探针影响，不与无探针样本混算。

这是单进程、同一数据库、热缓存下的固定测量，时间区块不是独立部署。报告收益采用本轮同时运行的旧版与新版，不与历史测量直接相除。未重新评估所有常规强基线，不声称生产吞吐、总体算法优越性或完整 API 准入。

## 阶段结论

可以复用纯源码解析产物，同时保持当前实时核验行为。两者的有效期边界在实现和测试中已分开。

完整路径仍比原 helper 慢。独立 profile 显示，剩余成本主要落在绑定器内，包含目录核验与运行时源码检查；本轮没有据此继续缓存这些条件，也未改变数据库核验有效期。一次实现、验收与固定测量已结束。
