# NewOrder 职责拆分的接口验证

2026-11-03，实验 `5d3d0db9587a`。在上一轮观察提出的职责划分中，只验证“订单构造 ↔ 库存调整与属性供给”这一条边界。实验源码位于 `prototype/tpcc/module-split`，正式应用、冻结反编译输出与原重建包保持不变。

## 这次检验的问题

库存职责能否隐藏 SQL 和库存内部计算，同时向订单侧提供必要数据，并在已有契约下维持建单、重复商品和业务中止？本轮用实现和差分观察检验接口的可行性，不以有限用例反推出模块必不可少或未观察数据无用，也不声称找到最优粒度。

控制端仍是已通过反编译重建验收的 `c3cb2330433f`。实验端从已有候选源码人工抽取 NewOrderStock；除 NewOrderService 及其两个嵌套类重新编译外，只新增一个库存类。其他业务类、Sql、入口、事务框架、观察器、参考 JAR 和依赖都通过哈希确认未变化。运行加载日志确认实际加载了新库存类。

## 实际接口与职责

| 接口动作 | 输入/输出 | 库存职责内部 | 调用方责任 |
|---|---|---|---|
| 创建一次库存工作对象 | 共同事务 Connection、地区 | 创建自己的更新语句，确定地区属性列 | 借出正确事务连接，保有提交/回滚所有权 |
| `stage(item, quantity)` | 每行商品、数量 → 地区信息字符串 | 锁定/读取库存、计算数量与累计更新、排队 | 按订单原行序调用；不得去重或合并重复行 |
| `apply()` | 无额外业务参数 | 执行已排队库存更新一次 | 本轮约定在订单行批次之后调用 |
| `close()` | 无 | 释放自身语句 | 不将释放对象误当提交或回滚 |

库存职责不向调用方暴露旧库存、计算后的数量、回补阈值、累计字段、SQL 或 PreparedStatement。订单职责仍负责客户/仓库存在性检查、编号、订单头和待配送记录、商品价格与金额、订单行；结果构造继续由原 CandidateApp 完成，事务继续由原 AppRuntime 协调。没有声称本轮把所有职责都封装成独立模块。

连接是借用资源。NewOrderStock 没有 commit/rollback/连接 close 调用；SQL 异常仍向外传播。重复调用 apply 或 apply/close 后继续 stage 会被拒绝。这是新增接口的生命周期约束；数据库对照仅执行其约定的正常调用路径，未穷尽所有错误使用。

## 真实数据库对照

从已有 holdout 清单选出全部 NewOrder 命令，保留原相对顺序和时间，两端分别恢复同一快照，共 11 条/端：6 次提交、3 次业务中止、2 次输入拒绝。覆盖普通建单、库存回补、15 行订单、不同地区/客户、重复商品、首/中/末无效商品、零数量和非法行结构。

- 返回值、逐步写入观察、九表初始/最终完整行摘要、五项不变量一致。
- 控制端选中命令的响应和观察另与原冻结 holdout 证据核对一致。
- 重复商品 6 两行购买 1、2 后，库存仍为 78→76，累计数量 0→3，订单次数 0→2。新接口保留了延后批次的当前语义。
- 六次成功均只有一次业务 commit；三次中止均只有一次业务 rollback，观察前后状态相等；两次拒绝没有业务 JDBC trace。
- SQL 执行及执行结果、提交/回滚顺序一致。参数绑定与 addBatch 的相对位置有调整，未要求原始 JDBC 日志逐字相等。
- 库存 `stage` 提供的地区信息通过完整订单行结果和状态对照核查；仍未证明全部地区值和全部数据状态。

SQL 执行顺序检查是本轮控制变量、便于归因的保守选择，不等同于宣称相同 SQL/顺序是普遍业务能力要求。后续若依据目标契约改变顺序，应单独验证允许变化的条件。

原版运行 `a636e2f4d9cf`，拆分版运行 `514cbdb37bc1`。共 22 条输入，12 次提交、6 次业务回滚、4 次输入拒绝。本轮容器、卷和网络均已清理。

## 对模块粒度的判断

**有一个成立的局部结果：** 订单构造不再直接管理库存字段、锁查询和数量公式，只消费地区信息并协调库存工作的生命周期。这支持把库存作为逻辑职责单独表达。

**也有一项明确成本：** 接口不是 `扣库存(商品,数量)` 这样的无状态调用。当前重复商品语义要求先逐行读取并暂存、最后统一更新；同时订单行还需要库存侧的地区属性。契约因此必须表达行顺序、共享事务和写入阶段，单列输入/输出类型不足以描述边界。

这项成本没有因为类拆开而消失。实际需要讨论的是：保留这些规则时，有状态的库存接口是否足够清楚，还是应由更外层的建单协调明确统一管理写入阶段。后一种方案可能只是把复杂度移到协调层，不能仅按方法数量更少就判定更好。本轮没有实施或比较第二种方案。

新增类和通过测试只能证明这个接口在所选范围内可行。没有比较开发维护成本、替换另一种库存实现、独立部署或性能；不能据此判定已得到最优模块粒度或研究创新。

## 能力与证据边界

- 保持既有输入契约和数据操作，没有依据现有样本删掉未执行路径或未出现数据。单仓库是原先明确限定的范围，不是本轮通过测试后裁剪所得。
- 本轮三个无效商品中止仍发生在库存批次执行之前；没有验证库存写入后失败、结果查询失败、提交失败或网络故障。
- 共同事务与 SERIALIZABLE 设置沿用冻结框架，但本轮为串行，不能证明并发或锁竞争行为。
- 结果查询仍发生在提交前；是否必须保持其失败时的回滚行为仍待能力契约决定，本轮没有偷偷移动该边界。
- 逐步观察器仍有订单 ID >=3001 等夹具限制；完整九表最终摘要补充整体检查，但有限快照不能代表所有数据。
- 重复商品与金额浮点规则保持原状是本轮隔离变量的选择，不将它们自动提升为未来产品规范。
