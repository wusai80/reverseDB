# Tag 计数：强基线与成本初筛

2026-11-03。**B2 相对原 CASE 实现明显减少成本，但相对常规优化的优势较小，并非所有场景都成立。** 本轮 12 项 pytest 通过，保存 700 次无 trace 完整读取样本。四组数据中，小规模 B2 比最快常规方案慢 20.55%；其余三组中位耗时低 6.86%、11.07%、4.19%。这是单次本机热缓存初筛，不是独立重复验证后的生产性能结论。

## 对齐的契约与五种实现

沿用[绑定契约](TAG_BINDING_AUDIT.md)：active superuser、全部 Tag、固定数据、成功执行、立即返回按主键排序的完整 `(pk, count)` Python 整数序列。权限成员关系继续调用原 `permitted_document_ids`，零值与 COUNT DISTINCT 保留。没有把 B1 的异常豁免用于本实验。

| 实现 | 计算方式 | 单次 SQL 数 |
|---|---|---:|
| B0 | 原分组计数 → Python 字典 → CASE 回填 | 2 |
| ORM_join | 标准 ORM 的过滤式 Count distinct 与外层聚合 | 1 |
| ORM_subquery | 标准 ORM 的按 Tag 相关子查询与 Coalesce | 1 |
| Python_merge | 原分组计数 → 字典；第二次取 Tag 键后直接合并最终列表 | 2 |
| B2 | 原分组 SQL 保留为 CTE，LEFT JOIN 回填 | 1 |

三个常规方案实现于 [tag_count_baselines.py](../prototype/aggregate_reattach/tag_count_baselines.py)，未修改 B2。Python_merge 可以省略 CASE，因为已绑定的消费者只需要最终列表；它不能直接代替返回可继续过滤的 QuerySet。它与 B2 在本轮最终输出边界内对齐，是必须纳入的强基线。

先在八类边界数据上核对五种实现，包括空集合、零关联、软删除、同名标签、稀疏和密集关联；每个成本场景也在计时前逐一校验结果。期望计数独立从数据构造过程累计，每个计时样本在计时结束后仍核对完整结果。

## 预先固定的测量方式

- 四组规模、数据种子 42/43/44/45，固定每文档关联数；每四篇文档中一篇软删除，active superuser 可见其余文档。每组使用新 fixture。
- 每种实现先预热 3 次，再运行 5 个时间区块，每区块 7 轮；每轮固定种子打乱五种实现的顺序。每实现每场景 35 个样本，共 `4 × 5 × 35 = 700` 次计时。
- 区块在同一进程、同一数据库中执行，**不是五次独立部署**。每次构造新的 QuerySet，避免复用已求值结果缓存；共享数据库/进程处于热态。
- 计时包含 Python 查询构造、编译、数据库执行、fetch 和整数列表转换，不包含建数、期望值比较、trace 或 EXPLAIN。断言 Django query logging 关闭且 execute wrappers 为空。
- 所有方案共享相同数据、索引、连接和数据库配置；建数后统一 ANALYZE，无专用索引或 planner 调参。无并发、额外 RTT 注入或跨机器执行。
- Python 内存峰值与 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 在计时后单独采一次。内存仅为 tracemalloc 能追踪的分配，非总 RSS，也不含数据库或全部驱动原生内存。EXPLAIN 的时间不与主测量相加或相减。

环境：冻结 Paperless 镜像、Django 5.2.17、PostgreSQL 18.6；Read Committed、work_mem 4MB、shared_buffers 128MB、JIT on、max_parallel_workers_per_gather=2。应用与数据库使用同一 Docker Desktop 的内部网络。未控制宿主其他负载或 CPU 频率，不声称冷缓存、尾延迟或生产吞吐。

## 完整读取中位耗时

单位 ms。保留全部预定场景和实现，没有因某种写法较慢而删除结果。

| 场景（Tag / Document / 关联） | B0 | ORM_join | ORM_subquery | Python_merge | B2 |
|---|---:|---:|---:|---:|---:|
| small：30 / 80 / 400 | 4.046 | 1.936 | **1.755** | 2.498 | 2.116 |
| medium_sparse：300 / 2,000 / 6,000 | 18.173 | 4.073 | 49.031 | 4.739 | **3.793** |
| wide：1,000 / 5,000 / 25,000 | 67.733 | 14.310 | 38.824 | 16.143 | **12.726** |
| dense：300 / 3,000 / 90,000 | 40.410 | 37.470 | 130.092 | 27.340 | **26.195** |

“最强常规基线”取每个场景三个常规方案中实际中位耗时最小者，这是事后比较下界，**没有实现能提前选择它的策略**。

| 场景 | 最快常规方案 | B2 相对该方案的中位耗时 | B2 更快的时间区块 |
|---|---|---:|---:|
| small | ORM_subquery | 高 20.55% | 0/5 |
| medium_sparse | ORM_join | 低 6.86% | 4/5 |
| wide | ORM_join | 低 11.07% | 5/5 |
| dense | Python_merge | 低 4.19% | 5/5 |

比例由未舍入样本计算。各区块的“最快常规方案耗时 / B2 耗时”范围分别为 0.773–0.923、0.997–1.073、1.093–1.147、1.023–1.068。这些区块共享进程与缓存，不能据此给出独立样本的置信区间或统计显著性结论；尤其 4%～7% 的差距仍需要独立复验。

## 成本线索与解释边界

wide 场景中，B0 两条 SQL 模板合计 39,571 字节、2,001 个参数；B2 为 704 字节、0 个参数。ORM_join 为 483 字节，Python_merge 两条合计 533 字节。这支持 CASE 展开随目标键数增大的结构性成本，也表明常规改写已经能消除大部分该成本。这里统计的是 SQL 模板长度，不是协议层完整网络字节。

同一场景的单次 Python 分配诊断峰值：B0 约 3,815 KiB，ORM_join 75 KiB，ORM_subquery 90 KiB，Python_merge 315 KiB，B2 52 KiB。这是辅助诊断，不作为总内存节约比例或独立收益证明。

执行计划中，ORM_subquery 的聚合分别按 30、300、1,000、300 个目标行重复执行。medium_sparse/dense 中还出现每个目标行重复扫描文档关系；wide 中使用文档索引查询。该差异与“相关子查询小规模可快、大规模可能昂贵”的观察一致，但不能单凭此诊断精确分摊主计时中的 CPU、I/O 和编译成本。

不同场景同时改变目标数、文档数和关联密度，不能把表格当成单变量扩展曲线；尚未确定选择方案的交叉点。

## 当前判断与阶段定位

用户在本轮之后明确：当前尚未开始专门优化，不应以首版效率限制继续推进。以下判断据此区分原始观察与后续安排；原始数据及归档证据不变。

1. 首版 B2 在本次小规模场景慢于常规方案，不能声称当前实现普遍更快；这不构成对后续优化空间或方法可行性的否定。
2. B0 的大幅改善不能单独作为 ReverseDB 的贡献；常规 ORM 和直接 Python 合并已取得大部分收益。
3. 当前定位是可行性与成本定位，撤回以初筛收益作为 B3 前置门槛的安排。下一步完善受限转换与验证机制，专门优化随后开展；完整 API 与通用优化器的范围不因效率要求放宽。
4. 正负样本均作为后续优化对照保留。将来报告收益时仍需同契约强基线与独立复验，不根据四个样本硬编码选择阈值，也不预设优化必然成功。

本轮完成的是强基线对照和受控成本初筛，不提供方法新颖性或完整能力等价的结论。
