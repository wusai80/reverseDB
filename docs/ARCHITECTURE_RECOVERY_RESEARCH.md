## 1. 先修正研究对象

过去的实验先人工选定库存规则/模块，再确认某种拆分在固定数据上保持结果。它们证明环境、差分与局部实现可用，却没有检验“方法能否自己提出合理的模块边界”。这一顺序容易把人的领域知识和选择当成方法的能力。

新的研究对象应为：给定编译制品、可获得的结构/运行信息，以及少量明确的系统目标，恢复一组有证据支持的模块模型与接口契约，并解释不同粒度之间的取舍。

需严格区分两个产物：

- **实现描述**：现有程序可能/实际如何运行，包括状态、副作用、调用协议、异常和资源所有权。
- **目标契约**：希望新实现保留哪些任务与保证、允许改变哪些偶然实现行为，由需求、接口规范和人工判断参与制定。

实现代码和日志都不能独自判断某项历史行为是必须保留的规范还是待改缺陷。恢复现状、选择目标能力、设计新架构是相关但不同的任务。恢复模型也未必唯一；原目录/类划分不是唯一正确答案。

## 2. 已有研究覆盖了什么

| 研究线索 | 已提供的基础 | 对本项目定位的约束 |
|---|---|---|
| Parnas 的模块划分准则 | 模块划分可以围绕隐藏设计决策，而非简单照搬处理步骤 | “拆成几个类”或“每条 SQL 一个模块”本身不是贡献。[原论文转载](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html) |
| Software Reflexion Models | 将工程师的高层结构模型映射到代码模型，显示一致和偏离关系 | 人工模块草图加静态关系核对已有成熟思路。[作者论文页面](https://www.cs.ubc.ca/~murphy/papers/rm/fse95.html) |
| Bunch | 从软件依赖结构进行聚类，辅助恢复系统结构 | 调用图/依赖图聚类本身不是新方法。[原论文](https://ieeexplore.ieee.org/document/792498/) |
| Interface Automata | 用模型表达组件输入假设、输出保证和交互顺序，并讨论兼容性 | 给接口加入生命周期或先后顺序也不是单独的创新。[原论文](https://web.cs.wpi.edu/~heineman/html/teaching_/CS562/p109-de_alfaro.pdf) |
| Daikon | 从实际执行数据提出可能成立的不变量；文档明确指出结果可能有假阳性、假阴性 | 动态推断不是所有输入上的能力证明。[官方 FAQ](https://plse.cs.washington.edu/daikon/faq.html) |
| ArchAgent，2026 | 从源码/文档出发，结合静态关系、分组与 LLM 生成多视图和业务相关架构 | “静态分析加 LLM 生成业务模块图”也已有直接相关工作。[论文全文](https://arxiv.org/html/2601.13007v1) |
| Bin2Wrong，2025 | 研究 Binary-to-C 反编译器的语义错误及系统性测试 | 反编译文本不能自动当作无误事实；该论文研究原生二进制，不能将其测量结果直接套到当前 JVM 案例。[官方论文页](https://www.usenix.org/conference/atc25/presentation/yang-zao) |

这次核对明确了不能直接作为创新的组成部分。尚需进一步检索“架构边界与契约共同推断、协议挖掘、组合验证和二进制组件恢复”的近邻工作，才能判断下面假设与已有算法的实质差别。文献名称不是创新性的证明。

## 3. 候选核心：联合推断边界与契约

**研究假设 H1：与先固定模块边界、随后补写接口契约相比，利用契约中暴露的跨边界状态、时序与资源假设反过来调整边界，能否在相同人工和执行预算下，减少关键依赖遗漏及隐藏的调用方义务？**

输出不仅是模块框图，还应包含：

1. 至少两种有理由的粒度候选及代码/字节码映射。
2. 每个候选模块的前置条件、状态读写、可观察副作用、调用协议、错误传播和资源所有权摘要。
3. 实现观察与目标要求的区别；每条事实的来源、适用前提与未验证项。
4. 为检验有争议边界而提出的判别问题，以及反例到边界修改的可追溯过程。

核心应是“如何修改边界/契约候选”的算法及其效果。把现有工具串联、生成 UML 或做一次成功重构，不足以支持 H1。

## 4. 可复用的方法结构

### 4.1 反编译作为证据入口

以字节码/反汇编及其位置作锚，建立规范化中间表示；反编译源码作为可读视图。记录无法确定的类型、间接调用、反射、动态生成查询和外部组件语义。第一阶段可以明确限定 JVM/JDBC，而不把一种制品上的可行性写成任意二进制通用。

变量名、类名与恢复出的函数边界只是线索，不预先当作业务模块。若反编译文本与低层证据冲突，保留冲突或停止相关推断；不靠自然语言解释抹平。

### 4.2 建立多种关系的系统模型

除调用与控制关系，还包括值的来源/消费、共享状态的读写、资源获取/释放、事务/异常边界、外部服务和持久化状态连接。事务等跨切面可表示为关联多个操作的约束，不因两个操作共用事务就强制合并为同一模块。

关系按证据区分：静态可能、实际观察、在明确模型/假设下已验证、尚未知。实际观察到一条路径，不能升级为必然调用；静态分析只有在列明反射/原生调用等假设后，才能讨论保守性。无法解析的边不等于没有边。

领域层只提供粗粒度任务、对外入口、外部依赖与不可违反的目标保证；不允许预先提供最终模块名称/边界后再把其恢复算作算法成绩。数据库等成熟依赖先用接口与保证摘要表示，按分析需要选择展开，而不是复现其全部内部能力。

### 4.3 提出边界并提取契约，再反过来修正边界

先由结构关系、状态归属及粗粒度领域约束形成多个候选。对每个候选提取它要求环境知道什么、承担什么，再检查：

- 调用者是否必须了解大量内部状态或执行细节？
- 是否把同一约束的责任切开，却没有明确的协调协议？
- 是否混合了可独立变化的职责，导致接口难以说明？
- 哪些未知关系会影响这一划分？

迭代操作可包括合并、拆分、调整状态归属、引入显式协调职责或保留未知。对一个有问题的边界，改变划分和完善接口都是候选，不能预设只有合并或只有拆分才对。

粒度同时考虑内部职责复杂度、边界契约负担、目标任务的可解释性和可验证性。仅最小化跨模块边会退化为整个系统一个模块；仅最小化模块规模会退化为每条语句一个模块。应比较多个取舍合理的候选，并用独立任务/约束排除这些无意义退化解，不能用未经校准的加权分数宣称“最优架构”。

### 4.4 实验检验模型假设，不按样本裁剪能力

针对存在争议的跨边界义务选择实验，例如：同一资源能否被不同调用方安全交替使用、某项错误是否需要跨边界撤销、特定调用顺序是否必要。输入搜索、故障注入、局部替换和静态检查可共同提供反例。

有效反例可能意味着契约遗漏、划分不合适、观察范围不足或模型提取错误，不能自动归为应删除某段代码。未发现反例只更新限定条件下的证据，未知关系继续保留。没有经过证明或明确范围决定，不基于未执行而删除数据/路径。

## 5. 如何检验通用性，而不是继续围绕库存例子

下一项小研究应固定算法和输入格式，然后在不同机制的小程序上恢复模型，不先动真实应用重构：

- 共享状态的多步骤处理：检验状态归属与多入口依赖。
- 文件或流资源的获取、处理与释放：检验所有权、失败路径和生命周期。
- 回调/插件协作：检验调用方向与责任归属不一致、间接调用及未知边。

每类设计若干语义相同但物理组织不同的版本（重命名、移动函数、拆合类），以及只改变一项真实协议的版本。方法应能在前者保持关键契约与逻辑职责稳定，在后者识别差异；这比拟合某一张原始类图更接近研究问题。不要把同一家族的多个变体当作独立系统样本。

评估阶段把原设计/源码作为独立评判资料；分析端只获得预先约定的制品和粗粒度任务说明。当前 TPC-C 已经被充分阅读，只能作为开发案例，不适合再包装成盲测集。应按系统家族划分调试和保留评估样本，不能只换数据值。

### 对照、消融和失败标准

- 基线：单纯依赖聚类；先定边界再推契约；相同输入条件下的 LLM 架构恢复。人工粗模型与实现核对可作另一工程基线。
- 消融：去掉状态/副作用关系、去掉契约反馈、去掉主动判别实验，分别测量增益。比较时使用相同证据、人工提示和执行预算。
- 指标：关键依赖遗漏与误报、接口义务遗漏、协议变更检出、结构重排后的稳定性、人工纠正量和运行成本。未知比例和错误断言率同时报告，避免全部标未知也获得虚假的好分数。
- 架构图相似度只作辅助，不能把目录结构或唯一专家划分当成全部真值；模块替换实验可作为后续端到端检验。
- 若效果仅来自更丰富的输入而非边界/契约联合机制，或离开熟悉案例就明显下降，应收缩贡献声明；若近邻工作已实现同一机制，应转为复现/比较，而非继续声称创新。

这些是拟定的研究设计，尚未实现或运行。先明确表示、候选修改规则和评判协议，再决定是否投入新工具或扩大负载。
