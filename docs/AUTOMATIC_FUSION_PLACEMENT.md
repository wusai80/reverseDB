## 自动化到哪一层

```mermaid
flowchart LR
  S[冻结源码与已有语义单元] --> C[人工核验的能力与传值契约]
  C --> I[自动检查所有连续区间]
  I --> D[动态规划选择执行位置]
  D --> P[切分方案与拒绝理由]
  P --> B[已有后端布局兼容性检查]
  B --> G[生成既有 SQL / Java 执行代码]
```

[通用选择器](../scripts/fusion_placement.py)只处理有序单元、依赖边、语义义务、传值编码和调用成本，不包含 NewOrder、Payment、仓库或库存等业务分支。原图里的 `placement`、`eligible` 和预设区域不作为选择输入。

[能力目录](../scripts/fusion_placement_contracts.py)仍是人工维护、绑定冻结源码的前端：哪些单元已有数据库实现、该实现承担哪些语义、怎样转换边界值，都引用已有代码和实验依据。单元粒度、类型摘要、循环阶段及调用成本也仍需要前端提供。`verified_source_contract` 是该目录的信任声明，不是选择器生成的形式化证明。

因此，本轮自动化的是**给定语义单元与能力契约后的切点选择**，没有自动发现任意 Java 方法的完整效果，也没有独立证明目录中的语义声明。已有后端只会生成已实现的布局；选择器若提出其他布局，生成入口会拒绝，不能把一个逻辑可行方案冒充已实现、已验证的程序。

## 区间合法性

每个单元保留原 Java 执行方案，也可以有一个满足其语义义务的数据库方案。数据库区域只能包含连续、完整的单元，不能改动阶段内部次序或删掉操作。

区间必须同时满足：

1. 每个单元都有已核验的数据库转换规则，方法体和 SQL 效果已知；规则声明覆盖所有必需语义。
2. 所有单元属于同一外层事务，后端不得自行提交；源码依赖顺序不变。
3. 区间外传入、以及区间内产生但仍被后续单元使用的值，都有正确方向的传值编码。
4. 若配置传值槽位上限，不得超过上限；不能截断值、行或数据来满足限制。
5. 在合法参数下界处，原区间至少执行一次 JDBC 调用，避免把合法的零调用路径变成一次无条件数据库调用。

这里假定每个数据库区域都经 Java 协调端传入和接回需要的值，没有数据库会话缓存来跨调用保存私有中间值。传值槽位上限只计算完整值的数量，不是字节、行数或内存估计；当前两个案例未配置该上限。

一个关键例子是 NewOrder 的 `ordered_staged_lines`：它有区域内部表示，却没有跨 JDBC 边界的编码。单独下推读取阶段会要求导出该值，因此被拒绝；把完整读取和两个写入阶段放在同一区域内，则不需要导出。判定依赖值的生命周期，不依赖测试中的商品 ID。

Payment 的金额与信用／字符串单元没有合格的数据库能力，选择器保留它们。一个仅承诺“十进制计算、按码点截断”的候选，不能满足原 Java float32、UTF-16、可变客户对象及信用条件的义务。该检查核对的是声明的语义契约，不是自动理解任意候选 SQL 的算术。

## 优化目标与求解

本轮只优化正常执行路径上的 JDBC execute 次数。每个原 Java 单元的调用成本使用非负仿射式表示；每个数据库区域消耗一次外层 execute。提交、回滚与观察查询不在该目标中。

| 案例 | 完整合法参数范围 | 原调用式 | 所选调用式 |
| --- | --- | --- | --- |
| NewOrder | 订单行数 n ∈ [5,15] | 11 + 2n | 1 |
| Payment | 信用条件 b ∈ {0,1}，BC 为 1 | 8 + b | 3 + b |

参数范围来自现有应用／条件契约，不来自某一批测试数据的分布。没有用测得的毫秒数拟合权重，也没有把信用分支按样本频率裁掉。

目标按字典序最小化：

`（参数范围内的最坏调用次数，移入数据库的单元数，数据库区域数）`

后两个分量仅用于平局时偏向更少移动。单独迁移一条原本就只调用一次的查询不会因“能下推”而自动获选。

设 `D[j]` 为前 j 个单元的最优目标值。候选为：

- 原 Java 执行第 j 个单元：`D[j−1] +（该单元最坏调用数, 0, 0）`。
- 将合法区间 `[i,j)` 放入数据库：`D[i] +（1, j−i, 1）`。

由于成本系数非负、参数是给定区间，最坏调用数在参数上界处取得；区间的“不新增调用”检查在下界成立即可覆盖该仿射模型的整个参数域。顺序、类型与事务合法性先作硬约束，再比较成本。

预先给定区间合法性时，动态规划比较为 O(n²)。当前实现直接扫描区间及值的使用关系，总体检查开销还包含至多立方量级的活跃值分析；这轮没有做分析器性能优化。

该最优性只适用于给定的原子单元、连续区间、协调端传值规则及调用模型。它不是实际延迟、吞吐或任意执行布局的全局最优保证。

## 固定验证结果

[测试驱动](../scripts/test_fusion_placement.py)完成以下检查：

- **穷举对照**：NewOrder 的 10,946 个模型合法切分中，唯一最优目标为 `(1,12,1)`；Payment 的 442 个中为 `(4,7,2)`。穷举独立递归枚举所有选择，与动态规划共享区间准入规则，因此核验优化算法，不独立证明准入规则正确。
- **名称无关**：重命名单元、值、事务和后端标识后，切点位置不变。
- **能力变化**：撤销 NewOrder 一处后端能力后，工具保留该 Java 单元，提出两个数据库区域，模型调用数从 1 变为 3。该变化只作静态反例，没有生成或执行新的后端。
- **未知保留**：SQL 中出现未知函数、方法体未知、值生产者未解析时，不会因已有 SQL 或能力标签而放行。
- **边界与成本**：缺少编码、跨事务、自行提交、隐式删阶段、重复阶段均被拒绝；零传值预算保留所有原操作；无调用收益的独立查询留在 Java。
- **语义反例**：提前写库存违反完整读取阶段及读后写依赖；十进制／码点替换不满足保留 Java 语义的义务。

还用一个反事实的零行参数域检查“原路径可能零调用”的保护规则。这是成本模型反例，不修改真实 NewOrder 的 5～15 行输入域，也没有增加业务数据集。

调用式与既有运行记录一致：NewOrder 三个固定订单的六个原版／融合记录，以及 Payment 两臂共 36 次成功执行的实际 execute 数全部匹配。这只是对模型的已有证据核对，不是新测量。

## 两项目共同契约与迁移验收（2026-11-09）

统一链路固定为：**来源绑定的有序语义单元 → 输入／输出值与效果依赖 → 可核验的区域实现及传值能力 → 原DP选择 → 完整结果／状态差分 → 固定性能评测**。profile只决定先研究哪个候选，概率评分只可辅助安排核验顺序；它们均不单独授权删除。第一项目的语义阶段和后端目录原本就包含人工摘要，不能把历史成功描述成全自动恢复，再以不同标准评价新项目。

### 同一方法中的不变项与适配项

| 层次 | 两项目共同要求 | 可以因语言／后端不同而适配的部分 |
|---|---|---|
| 来源恢复 | 每个单元可追溯到版本、方法及代码；不把静态边当必执行边 | Java字节码／反编译入口、Python源码／字节码来源入口 |
| 语义表示 | 源序、带类型输入／输出、控制与读写／锁／异常效果、事务边界 | 类型编码、调用约定、SQL方言；unknown必须显式保留 |
| 区域实现 | 同一外部接口及约定范围内的可观察行为；不得裁数据、跨未知边界 | JDBC／PostgreSQL与Python／SQLite的编码、执行和解码代码 |
| 候选选择 | 同一个区间DP及调用成本目标；平局保留更多原实现 | 来源明确的调用成本与合法参数域，不用样本频率替代能力范围 |
| 验证 | 反例、完整输出／状态、固定回放与配对计时；失败记录保留 | 业务入口及测试夹具，不改变比较原则 |

不同后端适配器不等于不同选择算法，但目前的人工beets辅助函数也不能自动算作一个已接入的适配器。项目名、模块名、当前样本行数以及测得的12.37%收益都不得进入共享准入或选择逻辑。适配器不应返回希望选择的区域列表；候选只有一个也必须如实称为“在给定候选中的选择”，不能宣称完成了候选发现。

### 共同的区域契约

用以下描述统一已有契约字段及尚缺的域信息，**本节是设计约束，不是已新增的执行引擎或验证器**：

```text
C(R) = (来源绑定, 有序单元, 类型化输入/输出, 必须保持的效果与顺序,
        适用范围 Γ, 原调用成本, 可用实现及其证据)

实现准入义务：对 Γ 内全部合法输入及执行，
              Obs(原区域) = Obs(候选区域)

Obs = 返回值与顺序、异常、外部读写/锁/回调效果、可观察对象身份
```

`Γ`必须明确区分固定部署、合法输入域和错误／并发执行条件。不能将“正常路径调用数”这个**优化目标**误解成所有项目都已获得忽略异常的许可。第一项目保留其既有错误、事务和类型契约；beets目前仅有固定部署／成功读取的机制证据。统一的是描述方式和准入原则，不要求两个应用承诺完全相同的业务能力，也不为比较而削弱第一项目契约。

融合和删减可以作为同一外部语义区域的不同实现：区域内跨层传递及中间表示若无外部消费者，可以尝试在后端内部消除；涉及错误或外部效果仍必须履行契约。原选择器继续完整覆盖源单元，不通过偷偷删节点来制造低成本。某次内部删减为何等价属于实现契约的证明义务，不由DP计算结果倒推。

### 将已有结果对应到共同表示

| 已有对象 | 外部接口／必须保留的语义 | 替代实现与成本 | 实际状态 |
|---|---|---|---|
| NewOrder | 仓库／地区／客户／全部明细／时间输入，完整订单与明细输出；读取阶段、库存写入、检查与事务保持 | 内部12阶段合为一个区域；11+2n→1 | 原DP已选择；来源绑定后端及执行证据存在 |
| Payment | 金额、客户、信用条件、时间输入；Java数值／字符串／对象语义及完整输出保持 | 两个数据库区域，必要主机计算留原处；8+b→3+b | 原DP已选择；语义不闭合部分保留 |
| beets首项标量消费 | 专辑标识、排序、配置与数据库视图输入；首项tracktotal及原转换／空结果语义输出；复杂分支原路径 | 固定行读取→扩展读取→Item→标量，候选保留首查询和转换、删除扩展读及Item；适用首分支2→1 | 有条件的人工机制，完整导出12.37%耗时下降；严格错误反例仍在，无共享DP准入 |

第一项目已有后端也通过主机端编码／解码传值。因此，beets保留少量Python转换代码本身，不足以判定必须换一种算法。可能的统一接口是“原输入编码→一次数据库执行→已验证输出解码”；但仍需核查SQLite返回表示、原转换效果、错误范围和事务行为，不能把尚未验证的主机计算一律改名为解码后直接放行。

当前两个实质缺口是：beets嵌套SQL尚不属于现有共同效果解析器支持的语法，以及其删除读取／物化的实现尚无可接入原能力目录的闭合契约。前者应通过一般的关系操作表示或有来源依据的效果摘要解决，不能增加针对`albumtotal`名称、固定SQL文本或当前数据的白名单；后者须绑定语义域、实现及反例证据，不能从“输出测试通过”直接生成`verified_source_contract=True`。

### 关键新发现：初始化中的动态分派不能漏掉

虽然`Item.__init__ is Model.__init__`成立，原构造函数仍执行`self.update(kwargs)`。从Results构造Item时kwargs为空，但实际分派到`Item.update`，其条件是：

```python
if self.mtime == 0 and "mtime" in values:
    self.mtime = values["mtime"]
```

即使values为空，Python仍先计算左侧的mtime读取／转换，再确定右侧为假。观察到的转换次序是原版`mtime → tracktotal`，直接解码只有`tracktotal`。这不是凭空添加的构造路径，而是原源码的实际子类分派。

6个效果对照中，目标字段转换的效果／异常被原样保留；作用于所有字段的转换回调则暴露遗漏：原版先调用mtime，候选跳过它；按字段名抛错时，两边分别在mtime和tracktotal失败。覆盖tracktotal getter与令mtime getter抛错也继续构成反例。动态回调是显式注入的验证条件，**不能据此声称原固定无插件样本的返回结果已错误或抹掉既有性能记录**；但它否定了“继承同一个构造函数就足以关闭初始化效果”的推断，固定部署的源码契约也须覆盖这一动态调用边。

这与第一项目保留存在性检查、数值转换和事务顺序的原则一致：不能因某个中间值不进最终输出，就连同它的必要效果一起消除。下一步应从初始化与属性消费恢复必须保留的操作顺序，再判断对象容器是否可以消除；不为beets硬编码一个mtime特例，也不新建项目专用删除算法。

## 源码初始化效果恢复实验（2026-11-09）

本步解决上一轮确定的初始化漏项，复用第一项目“保留必要效果、消除中间表示”的原则。新增[受限源码转换器](../scripts/initialization_effects.py)，按接收者实际MRO定位方法及super目标，记录源码位置和函数哈希。它不识别项目名或字段名，不改概率估算模型、共同区间检查器或原DP；这是限定语法的源码转换实验，不是另一个删除选择算法。

### 恢复的效果与适用前提

Results构造Item时没有额外kwargs，因此传入update的是新建的精确内置空dict。父方法仅遍历该字典的items，循环体不会执行；子方法的条件仍须按源码求值。转换器只在最后一个and分量是字面常量对该空字典的成员判断时，确定分支体不可达；此前的字段读取、比较、短路及可能的异常全部保留。实际生成代码如下，字段名由源码取得：

```python
def run_initialization_prefix(_load):
    values = {}
    if _load('mtime') == 0 and 'mtime' in values:
        pass
```

这不只是补一次mtime转换：比较可以返回带有真值方法的对象，比较及真值方法均可有副作用或抛错。生成代码保留整个条件的原求值方式。随后将原clear_dirty中的私有存储改为局部记录，仍先创建空dirty集合，再判断原资源的真值，条件成立时读取同一资源的revision；未宣称资源操作纯净。局部记录的输入和不逃逸前提需要调用方提供，不能据字段名以下划线开头就证明私有状态不逃逸。

独立的[beets行包实验适配器](../prototype/beets/prefix_consumer.py)保留原两次查询形成的完整有序行包、扩展属性索引及原LazyDict。执行顺序是：构造局部惰性字段容器 → 初始化条件 → 私有状态步骤 → 消费字段。同一字段在初始化及后续消费中共享原惰性缓存，每次属性需求仍调用原getter注册表查询。候选实际不构造Item；本轮只消除实验中的对象表示，不省略数据库读取、不裁剪数据、不更改SQL投影或排序。

原样使用`beets-prefix-export/20261109-44ae25a1b8a2`中已经完成完整导出差分的入口、行读取器、源码初始化条件、私有状态步骤及原LazyDict消费；逐份核对代码、完整集成实验清单与最终离线审计关联。没有为了性能跳过刚恢复的初始化操作，也未新增缓存、索引、投影或LIMIT改写。前后完整原源码、5000份WAV媒体以及第一项目选择器核心均核对哈希。

沿用此前5000曲目、500专辑的完整五表数据和相同固定种子20261109。每次执行新建完整数据库副本及Library，同一进程、操作系统缓存不清空。先执行原版／候选各一次诊断，再进行2对预热和8对正式交替AB／BA，共22次完整ExportPlugin.run。每次导出全部默认JSON字段并写入文件；主计时包括候选安装／恢复，源码验证／一次性编译、数据库复制／打开、输出及状态核查位于计时之外。不含CLI启动或插件发现，也没有新增fsync。

计时轮仅使用两臂相同的查询整数计数器；详细SQL记录与模型物化计数只在两次独立诊断中启用。所有预定样本保留，没有排除慢轮次、按结果补测或调整候选。协议、统计方法和状态核查复用原评测，仅将实际加载的实现改为恢复效果版本并增加其来源核验。

### 结论与停止点

补回必要初始化操作之后，跨层删减仍在这批固定部署、成功读取负载上取得正向端到端收益。这个版本现在有自己的性能证据，不再借用旧候选的12.37%结果。**本轮没有同时重测旧候选**，两个比例来自不同批次和不同实现，差额不能全部归因于初始化恢复，也不是该操作独立开销的估计。

本轮固定评测结束，不追加同片段样本或性能驱动调优。成功读取、固定原生字段分派、接收者身份及已知读取错误边界继续按原范围处理；默认应用未替换，统一入口和共享后端准入仍未完成。新增性能结果不能消除这些语义义务。
