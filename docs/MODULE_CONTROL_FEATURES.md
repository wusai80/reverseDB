# 控制依赖扩展：从模块变量到可观察行为

2026-11-04。已加入一个独立的控制依赖提取原型，并将三项新字段并入上一轮案例的特征记录。**它能识别“模块写入 → 守卫 → 异常/返回”的依赖，也能区分同一动作的不同守卫上下文。** 21 项边界检查通过。当前只验证特征提取，没有重新拟合概率或批准删减。

实现：[control_features.py](../prototype/module_pruning/control_features.py)；固定范围：[control_feature_protocol.json](../prototype/module_pruning/control_feature_protocol.json)；运行入口：[evaluate_control_features.py](../scripts/evaluate_control_features.py)。原 `effect_features.py`、概率拟合器、`risk_model.json` 均按上一轮归档哈希确认未变。

## 表达什么

例如：

```python
reject = False
if not removed:       # 被研究的模块区域
    reject = x < 0
if reject:
    raise Rejected("REJECTED")
return {"accepted": True}
```

原特征只追踪返回值读取的名字，漏掉了 `reject`。新图记录三者的关系：

```text
模块中的 reject 定义 ──数据依赖──> if reject ──控制依赖──> 抛出异常
```

边按“提供者 → 使用者”定向。设模块节点集合为 M、显式观察节点集合为 O，D 为标量定义到使用的边，C 为条件到受其控制的语句的边。新特征记录是否存在从 M 到 O、由 D/C 构成且至少包含一条 C 边的路径。O 目前只包括显式 return/raise；沿途也可经过赋值后再到返回。它表示结构上的可能影响，不表示路径一定可达，也不表示删除一定违约。

| 新字段 | 含义 |
|---|---|
| `module_controls_observation` | 存在上述包含控制边的路径，输出节点、源码行及边的证据 |
| `module_may_return` | 模块本身含可在结构遍历中到达的提前返回，避免把直接终止执行误当无效果 |
| `retained_action_same_guard_context` | 后续保留动作与模块动作语法相同，词法守卫、真假分支及守卫变量的到达定义一致 |

最后一项只是更精确的上下文证据，**不是替代执行证明**。尚未证明守卫覆盖、路径可行性、动作读取的全部状态等价，以及两动作之间没有相关效果。相同条件的冗余守卫可以产生控制路径，但仍可能可删，说明“存在控制依赖”也不能直接变成必要性标签。

## 实现边界

采用受限结构化分支遍历与标量到达定义：

- 标量无条件覆盖会切断旧定义；条件覆盖在汇合点保留两侧可能定义。
- 各分支使用独立环境，避免把一个分支的定义错误连到其兄弟分支。
- 某分支提前 return/raise 时，后续语句仍受存活分支条件控制，即便已经离开原缩进。
- `if not removed` 只标识模块区域；按原程序区域被执行分析，不把实验删除开关当业务依赖。
- 同名守卫变量在两位置之间重赋值后，其到达定义不同，不能标记为相同守卫上下文。

这不是通用 Python/Java 分析器，也不是完整的基于后支配关系的程序依赖图。限定 `execute(x, flag, removed)`、整数/布尔输入、一个精确删除标记和固定异常观察包装。循环、任意异常处理、表达式中的隐含控制、堆/别名、隐式异常及外部调用尚未完整分析。条件表达式、非条件位置的短路表达式和除法（包括增量除法）不能静默归为无依赖。

三态处理：支持范围内返回结构特征 true/false；有未建模效果时，正向结构证据可保留 true，缺失证据返回 null；无法建立结构则整体 unknown。`effect_summary_complete=false`、`deletion_authorized=false` 始终保留。即便字段均为布尔值，也不表示完整语义或效果摘要已闭合。

此处 7/6/3 是新控制分析的范围。旧效果提取器原有 12/4 接受/拒绝记录不变；例如模块后的字典复制在新分析中只有部分事实，**并未因此获准进入完整评分**。

上一轮五个危险诊断建议的对应情况：

| 案例 | 新增证据或仍存缺口 |
|---|---|
| `control_dependency` | 捕获模块写入 → 分支 → 抛错；冻结源码第 8→9→10 行 |
| `early_return` | 捕获模块提前返回及其控制路径 |
| `opposite_guard` | 捕获控制路径；同动作的守卫上下文不匹配，与 `redundant_guard` 区分开 |
| `implicit_division_error` | 标记隐式算术异常未建模，新字段为 null；未解决除零语义 |
| `reset_after_assignment` | 没有新的控制路径；旧“中性更新”误判仍需时序/值分析 |

因此是 **3 个出现控制证据、1 个保持未知、1 个仍无新增控制证据**，不能称为“误删率从 5 降到 1”。新记录的 `updated_probability=null`，旧诊断分数仅作为历史字段保留，正式判定仍全部 abstain。不能将 null 补成 false 后交给原布尔校准器，也不能把新增特征直接套用旧单元的概率。

`overwritten_receipt` 与 `checksum_chain` 的控制特征仍相同：前者被后续覆盖、后者传递到返回，区别主要是数据时序。此次没有为了消除所有反例而继续扩展问题。
