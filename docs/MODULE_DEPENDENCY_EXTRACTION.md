# 从反编译产物提取模块依赖事实

2026-11-04。本轮把上一阶段的人工事实核对推进到**受限的自动语法与符号提取**。实际找到展示模块的两个消费者、弃用的调用结果、SQL 定义关联、共享调用与异常义务。依赖摘要仍不完整，因此自动判定保持 unknown，没有新增模块删减或性能实验。

后续[软工与实例联合论证](MODULE_DELETION_ARGUMENT.md)通过手工源码推理澄清了指定分支内的对象类型；这没有改变本报告的自动提取结果或补齐效果摘要。

随后完成[分支上下文自动提取](MODULE_BRANCH_CONTEXT.md)，另存新归档。本文所述首版结果保持其历史范围。

## 输入与方法

输入是此前重建归档中的反编译 `OrderStatus.java`，以及冻结的应用适配器 `TpccApp.java`。后者是保留的适配器源码，不冒充新反编译结果。另有一个独立的小型语法夹具，用于检查分析边界。所有归档来源、类文件和 JAR 依赖均核验原摘要。

[提取器](../prototype/module_pruning/DependencyExtract.java)使用本机 JDK 的 Java 编译器语法树和符号归属分析。先解析及类型检查，再记录方法符号、源位置、调用结果的直接语法用途、声明的异常、显式 throw、部分可见赋值及 SQL 定义。关闭注解处理，不运行被分析的业务类，不连接数据库。

这比文本锚点进一步：方法和变量按编译器符号区分，可以避免同名局部变量或不同类方法被误当成同一对象。但它还不是完整调用图、控制依赖图、活跃性分析或数据库效果分析。

## 自动提取到了什么

| 事实 | 提取依据 | 不能据此推出什么 |
|---|---|---|
| 应用调用展示方法后丢弃返回值 | 已审阅反射桥的调用结果处于独立表达式语句 | 不代表调用无异常、无状态效果或可以删除 |
| 原终端入口还有消费者 | 直接调用符号为 getOrderLines，结果赋给局部变量，后续出现同一变量符号的引用 | 引用数不是路径敏感的活跃性证明；引用记录可能包含写入 |
| 展示方法关联专属 SQL 字段 | getPreparedStatement 的实参解析到 ordStatGetOrderLinesSQL 字段符号 | 初始化 SQL 文本不保证运行中字段未被修改 |
| SQL 初始化值为 order_line 的简单 SELECT | 支持字符串常量、字符串拼接和受限 %s 格式化；匹配小型 SELECT 语法 | SELECT 不是“纯函数”：错误、RLS、视图、锁及观察者仍需摘要 |
| 方法声明 SQLException | 类型解析后的方法声明及调用符号 | 没有证明具体触发条件、所有未检查异常或异常处理路径 |
| 客户/订单模块显式抛错 | 语法树中的 throw 与所属方法 | 哪些错误是目标业务能力，仍由能力契约决定 |
| PreparedStatement 工厂有多个消费者 | 客户、订单、展示方法调用同一已解析方法符号 | 不应随展示模块一起删掉这个共享帮助方法 |

提取结果保留调用表达式、文件、行号和源码区间，供检查“删除理由”使用。所有调用的 `effect_summary_complete` 均为 false；没有因为未扫描到某种效果就宣称不存在。可见赋值记录只是线索，不能作为完整堆效果摘要。

## 反射处理：自动部分与人工部分

适配器通过一个统一的 `invoke` 方法，按对象声明方法中的“方法名 + 参数数量”查找目标。这个桥的行为摘要是**人工审阅输入**，并绑定整个桥方法的源码 SHA-256；没有声称提取器自动理解了任意反射代码。

在这个固定摘要下，自动处理以下内容：

1. 解析常量方法名和实际参数数量。
2. 对未被重新赋值的局部变量，追踪直接 new、局部别名及受支持的 switch 表达式分配集合。
3. 枚举这些具体类型声明的方法，按桥规则给出候选，同时记录缺失目标、同名同参数数目的歧义和可能调用失败。

动态方法名、未知接收者、对象重新赋值、匿名子类、打包 varargs 等超出本轮范围时标为 unknown。原桥改用 `getMethods` 后，源码摘要失效，提取器拒绝继续沿用原摘要。

**本轮实际发现的关键缺口是分支上下文。** `p` 初始化于一个四分支 switch。首版记录到 Payment、OrderStatus、Delivery、StockLevel 四个可能类型，但没有将初始化条件与随后 OrderStatus 调用分支关联：

```text
接收对象分配集合：{Payment, OrderStatus, Delivery, StockLevel}
请求方法：getOrderLines
有匹配方法的类型：{OrderStatus}
其余三个类型：没有匹配方法，可能使反射桥抛错
```

因此“找到一个匹配方法”不等于“证明调用必然到这个方法”。必须保留失败可能和路径未解析标记。这里说明恢复调用关系需要以具体应用入口和分支条件为上下文，不能把所有分支混在一起后直接做删除。

## SQL 与异常边界

SQL 分类只支持常量 SELECT 的有限语法：简单列投影、单表、基础比较、AND、单列排序和常量 LIMIT。它的结果名为 `restricted_select`，只表示形状；写入关键词标为 `may_write`，含函数、动态文本或其他未支持语法保留 unknown。没有把 SQL 关键词检测等同于关系或效果证明。

展示模块的 SQLException 声明和历史故障反例共同保留一项义务：若该调用可能失败，后续 JSON 生成可能受影响。新提取器目前只自动发现声明与显式 throw，没有证明跨方法的异常传播与终止性；此前人工约定的正常执行范围不会被自动升级为源码定理。

## 固定检查结果

[验证入口](../scripts/extract_module_dependencies.py)的 26 项检查通过，覆盖：

- 真实区域的两个消费者、丢弃结果、反射候选、SQL 字段关联、声明异常、客户/订单 throw 和共享帮助方法。
- 独立夹具中改名的方法和局部别名、被保留的结果、动态名称、未知或重新赋值的对象、匿名子类、打包参数与重载歧义。
- 简单 SELECT、含函数 SELECT、UPDATE、动态 SQL，以及格式化实参中的 `%s` 不得被再次当作占位符。
- 丢弃返回值仍可能抛错、反射桥摘要变化必须拒绝、摘要未闭合时不得自动批准删除。

最终扫描记录包含 214 个调用语法点、31 个经过该反射桥的调用，其中 22 个来自原适配器、9 个来自独立夹具。30 个方法树记录中 24 个有对应源码区间，其余是编译器引入的构造器等记录。这些数量不是恢复率或正确率。

与上一阶段判定器的连接仍很有限：复用人工需求图，将自动提取结果的 `dependency_summary_complete=false` 传入准入义务，结果为 **unknown / unclosed_obligation**。本轮没有自动生成并替换完整人工需求图，没有产出可直接部署的删减版本。

来源核验、语法事实、手工反射摘要及能力假设分别保留。测试通过不证明输入语法之外的解析正确性、全程序分析完备性或能力等价。

## 下一项研究问题已具体化

现在需要解决的不是增加缓存或继续测速度，而是：**能否在选定应用入口和能力范围内，恢复足够精确的调用与效果依赖，使一个候选区域的删除义务真正闭合？**

这个案例给出了两个明确缺口：

1. 将分支条件与接收对象来源关联，收窄反射目标，同时保留无法排除的错误路径。
2. 给数据库调用和外部库调用建立范围明确的效果摘要，说明哪些条件来自程序、哪些仍需环境契约。

这应继续围绕同一个删除候选研究，不必先实现通用 Java 编译器或完整软件架构恢复。AST 提取和普通调用图技术本身不是新的学术贡献；研究价值仍需由“条件化模块删除如何获得可靠依据”来体现。本轮到此结束，没有扩展业务范围。
